# 时钟：为什么最终把"时区补偿"全部删掉

> 这块板子的时间问题**修了五轮都没修好**，第六轮才定位到根因。
> 结论是：**问题不在"显示时区"，而在"写入环节"** —— 一层层互相打架的
> 补偿逻辑本身才是 bug。最后把这套补偿**全部删掉**，只留一个事实来源。

---

## 一、最终状态（就这么简单）

| 项 | 状态 |
|---|---|
| 系统时钟的**绝对数值** | 等于北京时间的墙上读数 |
| `/etc/TZ` | **不存在** |
| `/etc/localtime` | **不存在** |
| RTC 芯片 | 存的值与系统时钟**一致**（无任何换算） |
| 开机流程 | 内核 `RTC_HCTOSYS=y` 直接读 RTC 设系统时钟，**没有任何用户态脚本参与** |
| 补偿脚本 | **全部移除**（见下表） |

实测三方对账（重启后复测，差值 ≤ 2 秒）：

```
date            Tue Oct  6 15:40:01 UTC 2026
date -u         Tue Oct  6 15:40:01 UTC 2026
hwclock -u -r   Tue Oct  6 15:39:59 2026
PC（北京）       15:40
```

`date` 和 `date -u` 输出**完全一致**，这正是"没有时区参与"的标志：
系统里根本没有"本地时间"这个概念，谁都别再做 ±8 的换算。

因为没有任何时区偏移，**摄像头 OSD 水印烧进画面的那串数字，就是北京时间** ——
这也是用户真正要的结果（水印是烧录在视频流里的，浏览器端没法改）。

### 被删掉的东西

| 删除对象 | 它原来干什么 | 为什么必须删 |
|---|---|---|
| `/etc/TZ`（内容 `CST-8`）| 让 busybox/程序按 UTC+8 显示 | 它让"系统时间"和"显示时间"产生 8 小时差，成为后续所有混乱的源头 |
| `/etc/localtime` | 同上 | 同上 |
| `S14timezone` | 开机写时区 | 依赖 `/etc/TZ`，连锁 |
| `S99rtcinit` | 开机按 RTC 校正系统时间 | 与内核 `RTC_HCTOSYS` 重复，且用 `date -s` 语义有歧义 |
| `S49ntp` | 网络校时 | 源解析失败时不报错退出，**继续用错误基准反复纠正**，把时间越改越歪 |
| `gps_tz.py` | 按 GPS 经度算时区并写 `/etc/TZ` | 就是"自动 +8"这套逻辑，属于要删的补偿层 |

上面这些脚本在设备上都已移到 `/userdata/disabled_initd/`（改名 `.disabled`），
**不再进入启动链**；仓库里也一并移除，避免"仓库说要设时区、设备其实不设"的矛盾。

## 二、根因的证据链

关键证据只有一条，而且一直在手边：**`/proc/stat` 里的 `btime`**。

`btime` 是内核记录的**启动时刻**。排查时读它：

```
btime = 14:59 UTC     <- 开机瞬间系统时间就已经快 8 小时
RTC   = 07:05 UTC     <- RTC 里存的是正确的 UTC
```

**开机那一瞬间就已经错了**，说明错误是在"读 RTC → 设系统时钟"这一步产生的，
任何开机之后运行的脚本都只能"事后纠正"，重启必然复发 —— 这也解释了为什么
改五版脚本都没用：**一直在治症，没治因**。

同时确认了两条容易踩的语义陷阱（都实测过，不是推测）：

1. **busybox 的 `date -s` 把参数当"本地时间"解释**，而 `settimeofday(2)`
   系统调用没有时区歧义。用 `TZ=xxx date -s ...` 这种前缀在 init 脚本里
   **不可靠**。
2. **`hwclock -w` 写进去的是本地时间，`hwclock -u -w` 才是 UTC。**
   实测：系统 07:09 时执行 `hwclock -w`，RTC 变成 15:09（+8h 被固化进去了）。

### 一个自己制造的事故（记下来警醒）

排查中曾用错 `RTC_SET_TIME` ioctl，把垃圾值写进 RTC：

```
RTC = 121712915204   ->  板子认为自己是 2016 年
```

后来用 `hwclock -u -w` 修复。**教训：改 RTC 前先 `hwclock -u -r` 存下原值**，
否则会把"时间不对"升级成"时间彻底不可信"。

## 三、为什么"删掉"比"补对"更可靠

原来的设计里有**四层各自做换算**的东西：

```
内核读 RTC（把 RTC 当本地时间？还是 UTC？）
   └─ /etc/TZ = CST-8        （显示时 +8）
        └─ S99rtcinit        （开机 date -s 再设一次）
             └─ S49ntp       （联网后再纠一次）
```

四层里**任何一层的假设变了，整条链就错 8 小时**，而且"修好一层"往往只是
把错误转移到下一层 —— 表现就是"每次改完看着对了，重启又坏"。

删掉之后只剩一条：

```
RTC == 系统时钟 == 北京时间读数    （零换算）
```

**只有一个事实来源，就不存在"两层不一致"这种故障模式。**
这也是这个仓库里反复出现的同一个经验：约束越少、层数越少，越不容易坏。

## 四、怎么验证

板子上直接跑（不需要改任何东西）：

```sh
# 三方对账: 三者必须一致（允许 1~2 秒差）
date; date -u; hwclock -u -r

# 开机时刻是否已经正确（关键证据）
python3 tools/diagnose/check-boot-time.py

# 确认没有时区文件、没有补偿脚本在跑
ls -l /etc/TZ /etc/localtime          # 都应报 No such file
ls /etc/init.d/ | grep -Ei 'rtc|ntp|tz'   # 应为空
ps | grep -E 'ntpd|rtcinit|gps_tz' | grep -v grep   # 应为空
```

**重启一次再跑一遍** —— 时间问题最大的特点就是"看起来修好了、重启就复发"，
不重启的验证等于没验证。

## 五、如果以后要把时间改回"标准 UTC + 时区"

现在系统时钟存的是**北京时间的读数**，而它自称 UTC。如果以后要接 NTP、
或跟别的系统对接，这个"自称 UTC 的北京时间"会出错。

要改回来的话，**一次性**做完这三步（不要再分成多层脚本）：

```sh
# 1) 系统时钟减去 8 小时 -> 真的变成 UTC
date -u -s "$(date -u -d '-8 hours' '+%Y-%m-%d %H:%M:%S')"

# 2) 把真正的 UTC 写进 RTC
hwclock -u -w

# 3) 建立时区（二选一）
echo "CST-8" > /etc/TZ          # 简单固定偏移
# 或者把 tzdata 的 Asia/Shanghai 软链到 /etc/localtime
```

关键是 **RTC 和系统时钟必须同时是 UTC**，且时区只影响"显示"——
**只要保证"只有一层做换算"，就不会再出现这次的 8 小时问题。**
