# 单客户端接管 (一个时刻只有一个页面上车)

> 需求原话: "我想只要一个浏览器能访问他新的浏览器访问旧的就断开"
>
> 已实现并实测。全部在板子上用 Python/JS 完成 —— **没有碰 C5 固件, 没有刷机**。

---

## 0. 为什么不能只做"谁新谁赢, 直接踢掉旧的"

这是整个设计的关键, 先看 `index.html` 里这段现成的代码:

```js
whepFail = Math.min(whepFail + 1, 3);
retry = setTimeout(playWHEP, whepFail >= 2 ? 5000 : 2000);   // 无限重试
```

图传重连是**无限**的。如果只按下发时间踢掉旧的, 就会变成抢来抢去:

```
A 被踢 -> 5s 后自动重连, 变成"最新的" -> B 被踢 -> 2s 后 B 又抢回来 -> ...
```

两个浏览器每几秒互相踢一次, 谁都看不成。所以**必须让被踢的那一方知道自己
被踢了, 主动闭嘴**, 而不是靠时间窗硬压。

---

## 1. 设计

### 所有权 = 一个页面 id

每个页面加载时生成一个随机 `TAB_ID` (见 index.html), 随请求头 `X-Page-Id`
上报。板子记住"当前所有者是哪个 TAB_ID"。

粒度是**页面标签**, 不是 IP: 同一台电脑开两个标签也要互踢, 而两个标签的 IP
一模一样, 用 IP 区分不了。

### 认领只发生在两个地方, 而且都是"人主动做的动作"

| 入口 | 时机 |
|---|---|
| `POST /api/pageinfo` | 每次页面加载只发一次 |
| `POST /api/takeover` | 横幅上"点此接管回来"按钮 |

**自动重连永远不会走到这两处**, 所以它抢不回所有权。这是避免互踢的根本。

反面对照: 如果让每秒一次的 `/api/status` 也能认领, 被踢的页面靠轮询就能把
自己抢回来 —— 又回到抢来踢去。所以 `owner_view()` 是**只读**的, 不认领。

### 三层保险

| 层 | 做什么 | 失效后果 |
|---|---|---|
| 1. 板子侧 | 非所有者的控制类请求一律 403; 认领瞬间**主动停车一次** | 只能靠页面的失控保护 (0.5s) 停车 |
| 2. 页面侧 | 轮询发现 `owner:false` -> 停图传 + 停控制 + 显示横幅 (≤1s) | 旧页面继续占带宽 |
| 3. mediamtx 兜底 | 后台线程每秒轮询 `/v3/webrtcsessions/list`, 踢掉不属于当前所有者的会话 | 防"旧页面卡死了自己不会停" |

第 3 层要 mediamtx 的 API (`mediamtx.yml` 的 `api: yes` +
`apiAddress: 127.0.0.1:9997`, 只绑本机)。**任何一层失效都只是"没踢掉",
绝不会变成"连不上"** —— API 拿不到时 `mtx_enforce()` 直接返回, 图传照常。

### 接管时车会停

`_stop_now()` 在认领的**那一刻**被调用。不能指望旧页面自己发 stop: 它已经被
403 挡掉了。所以停车必须由板子做。这也是为什么被接管的页面上写"车已自动停下"。

---

## 2. 三层之外的细节

### 为什么快照要在认领那一刻做

第 3 层判定"这个会话该不该踢"的规则只有两条, 而且**不需要时间戳**:

* 对端 IP 不是所有者的 -> 别的设备, 踢
* 对端 IP 是所有者, 但这个会话在**最近一次接管之前就存在** -> 旧标签页留下的, 踢

第二条规定了"接管瞬间还活着的会话都该死"。所以快照必须在认领的**同一刻**取
(`_snapshot_live_sessions()`), 而不是等 `enforce_loop` 下一秒醒来 —— 因为
**新页面紧接着就开始拉流了**。

为此 index.html 里专门做了顺序保证:

```js
if(!document.hidden) claimThenStart();   // 先认领, 再 playWHEP()
```

如果反过来 (先拉流再认领), 新页面自己刚建立的会话会被算进快照一起踢掉,
表现是"页面加载后图传要白等一轮 2 秒重连"。

### 为什么不比较 mediamtx 的 created 时间戳

它是带时区的 RFC3339 (`2026-10-08T22:03:28.056176343Z`), 在这块 uClibc 板子上
解析 + 时区对齐都是额外的出错面。而"接管瞬间还活着的都该死"这句话用
**id 集合**就能表达: 记下那一刻的 id, 之后只要它们还出现就继续踢, 消失了就
忘掉。少一个出错面。

### 所有权要存盘

所有者只在内存里的话, **每次重启这个服务, 所有者就没了** —— 而认领只发生在
页面加载那一刻, 已经开着的标签页不会再发 pageinfo。结果: 重启后两个标签页都
看到 `owner=true`("还没人认领"), 双双在图传, 策略静默失效, 直到有人手动刷新。

所以存 `/tmp/owner.json` (tmpfs): 重启服务保留, 重启板子自动清掉 —— 正是想要
的语义。pageId 是随机的, 恢复出来的 id 只会匹配同一个标签页。

## 3. 实测

三套测试, 全部通过。

**A. 所有权状态机** (`tools/tests/test-owner-state.py`, 板子上跑, 20 项)
不变量: `owner_view()` 只读不认领; 同一个 pageId 重复认领**不算**接管
(否则每次自己刷新都会触发横幅 + 停车); 空 pageId 永远认领不了。

**B. mediamtx 踢人逻辑** (`tools/tests/test-owner-enforce.py`, 13 项, API 打桩)
覆盖: 分页信封 / 裸数组两种返回格式; 接管快照; 新会话存活;
无所有者时**绝不踢**(失败方向要安全); API 不通/返回垃圾时静默返回不抛异常。

**C. 策略端到端** (`tools/tests/test-takeover-policy.ps1`, 26 项, 从 PC 打真接口)
模拟两个标签页: A 加载 -> A 是所有者; B 加载 -> **B 接管, A 立刻变
`owner:false`**; A 发 `/api/move`、`/api/cmd`、`/api/speed`、`/api/quality`、
`/api/failsafe?t=5` **全部 403**; B 正常 200; A 点"接管"-> 抢回, B 变 403。
另外确认 `/api/status` 和 `/api/ping` **不受影响**(前者是通知通道, 后者是
诊断探针, 挡掉只会让排查变难)。

**D. 真会话踢人** (`tools/tests/test-takeover-e2e.ps1`)
真发一个 WHEP 请求造出**真实** WebRTC 会话, 然后让另一个标签页认领:

```
WHEP POST -> HTTP 201
  session Location: /car/whep/cd843864-6eb3-4d90-8a69-ea4fbf0a904f
live sessions: 1   id=e86e6644-...  remoteAddr=192.168.3.65:64479
pageinfo -> HTTP 200
live sessions after takeover: 0                      <- 真被踢掉了
板子日志: [owner] 踢掉旧图传会话 e86e6644-... (对端 192.168.3.65:64479)
```

## 4. 实现时踩到的坑 (都已在代码里注释)

1. **`X-Page-Id` 头收不到。** `handle_one_request()` 的快路径只扫
   `Content-Length` 一个头, 其它全丢 (`_Headers` 是个只认 content-length 的
   桩)。于是**每个请求都被当成"没有页面标识"**, 所有控制请求一律 403 ——
   连所有者自己也被挡, 而日志里一行错都没有, 只表现为"按了没反应"。
   加头必须同时改扫描循环和 `_Headers.get()`, 两处成对维护。

2. **mediamtx 返回的是分页信封, 不是裸数组。**
   `{"itemCount":0,"pageCount":0,"items":[]}`。原来按数组解析, 于是永远
   "没有会话", 踢人静默失效 —— 表现是"接管了但旧的图传没断", 同样零日志。
   两种格式现在都收。

3. **快照时机**(见上): 必须在认领那一刻 + 页面先认领后拉流。

4. **`S23web` 的 `kill_web` 会误杀自己人。** 原来用
   `ps | grep '[w]eb_server.py'` —— 挡得住 grep 自己, 挡不住**命令行里恰好
   提到这个路径**的进程。我在 adb shell 里跑 `python3 -m py_compile
   /userdata/car/web_server.py && /etc/init.d/S23web restart`, 那个 shell 就被
   当成服务 kill -9 了。改成读 `/proc/<pid>/cmdline` 并要求第一参数是 python3。
   (这是本项目第三次踩同一类坑, 前两次见 `S26mediamtx` / `S24spinet_wd`。)

5. **`S23web` 的 setsid 竞态: 服务会静默不启动。** busybox 的 `setsid` 是
   "先 fork 再 setsid"; 脚本 launch 完立刻退出时, 那个还没 detach 完的子进程
   会被连带杀掉。症状极具误导性: web.log 最后一行还是
   `[http] 监听 0.0.0.0:80`, 看着启动成功了, 但 `:80` 根本不监听。
   现在 launch 之后**轮询校验**最多 12 秒 (正常 2 秒就通过), 启动失败会明确报错。

## 5. 已知边界

* **粒度是页面, 不是人。** 同一个人开两个标签也会互踢 —— 这是刻意的 (用户
  明确要求), 也符合"同一时刻只有一个遥控器"。
* **每次接管都会停一次车** (即使旧页面当时并没有在动)。安全上是对的,
  但如果两个人在互相抢, 车会反复停 —— 实际场景里不会发生。
* 横幅只在**轮询到 `owner:false`** 时出现, 所以最长有 1 秒延迟。
* 第 3 层需要 mediamtx 的 API; 如果 `mediamtx.yml` 被改回 `api: no`, 前两层
  照常工作, 只是少了"旧页面卡死"时的兜底。
