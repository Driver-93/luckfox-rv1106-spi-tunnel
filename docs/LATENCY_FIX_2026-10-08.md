# 延迟专项 —— 200ms+ 的三个真实成因 (2026-10-08)

> 起因: 用户反馈"把延迟问题解决下 现在200多 尽可能的降低延迟"。
>
> 结论: 200ms 不是编码器、不是码率、也不是 SPI 时钟。它是**三个叠在一起
> 的独立缺陷**, 其中两个与"图传走 TCP 还是 UDP"和路由表有关, 与视频本身无关。
> 三个都已修好并实测。

---

## 1. 头号成因: 图传被钉死在 ICE/TCP 上 (200ms 与 RTO 完全吻合)

### 症状

浏览器能看到画面, 但延迟稳定在 200ms 级别, 且**周期性卡一下**。

### 根因

`board/config/mediamtx.yml` 里有这么一段 (现已删除):

```yaml
# 只留 TCP 候选。
# WebRTC 媒体默认走 UDP, 而 SPI 隧道只转发 TCP —— 浏览器如果拿到
# UDP 候选就永远连不上, 表现为"视频一直转圈"。
webrtcLocalUDPAddress: ""
```

那句"SPI 隧道只转发 TCP"**是错的**。C5 固件 `spinet.c:36` 一直是:

```c
static const uint16_t FWD_TCP[] = { 80, 22, 8889, 8189, 8888 };
static const uint16_t FWD_UDP[] = { 8189 };      /* <- 8189/udp 一直在转发 */
```

也就是 `webrtcLocalUDPAddress` 默认端口 8189 **本来就已经映射好了**, 只是没人试过。

### 为什么这一条能值 200ms

关掉 UDP 后浏览器只剩 TCP 候选, 于是**整条图传 (视频 + RTCP + DataChannel)
挤在一条 TCP 流里**。板子上 `tcp_rto_min` 不存在 (没有
`/proc/sys/net/ipv4/tcp_rto_min`), 最小 RTO 就是 **200ms** —— 与用户报的
"200多" 完全吻合。修复前实测:`TCPTimeouts=287 TCPFastRetrans=331 TCPSynRetrans=278`。
隧道上任何一次丢包都会让 TCP 队头阻塞 200ms, 浏览器只好把 jitter buffer 撑大。

### 修法

```yaml
webrtcLocalUDPAddress: :8189    # UDP 媒体候选 —— 低延迟的关键
webrtcLocalTCPAddress: :8189    # 保留 TCP 作为兜底
```

### 先证明 UDP 真的通, 再改

改配置之前先做了 A/B 验证 (`_udp_listen.py`): 板子上临时监听 `udp/8189`,
PC 往 `192.168.3.69:8189` 发 3 个数据报。结果双向都通:

```
板子侧: recv 7 bytes from 192.168.3.64:59331  b'HELLO-1'  (x3)
PC 侧:  got PONG-1 / PONG-2 / PONG-3 from 192.168.3.69:8189
```

改完之后 mediamtx 自己打的日志就是证据:

```
INF [WebRTC] [session ...] peer connection established,
    local candidate: host/udp/192.168.3.69/8189,
    remote candidate: prflx/udp/192.168.3.64/51572
INF [WebRTC] [session ...] is reading from path 'car', 2 tracks (H264, G711)
```

## 2. 第二成因: 新连接根本连不上 (调试网线造成的路由黑洞)

这条比延迟更严重 —— 它是**功能性故障**, 只是被"老连接还能用"掩盖了。

### 症状

- 已经在看的网页继续正常 (视频照流)。
- **刷新页面 / 新开标签页 / 任何新连接** 全部超时, 包括 `:80 :22 :8888 :8889`。
- 板子自己 `ping 10.77.0.1` 完全正常, 隧道 `ip tx/rx` 都在涨。

### 根因 (两层)

**第一层: C5 的 NAPT 不改写源地址。** `spinet.h:31-34` 写明入站包在
`ip_napt_recv` 里**只改写目的地址** (192.168.3.69 → 10.77.0.2), 源地址保持
浏览器原样 (192.168.3.64)。这是 lwIP NAPT 的既定行为, 前提是"LAN 侧主机的
默认网关就是这台 NAPT 设备"。而插上调试网线后, 板子自己也在 192.168.3.0/24 里
(`eth0=192.168.3.88`), 于是:

```
板子回包 dst=192.168.3.64  ->  主路由表命中 192.168.3.0/24 dev eth0
                             ->  从网线出去, 源地址还是 10.77.0.2
浏览器: 我连的是 192.168.3.69:80, 这个回包来自 10.77.0.2 -> 丢弃
```

`/proc/net/tcp` 上是决定性证据 —— SYN 到了, 但卡在 SYN_RECV:

```
11: 02004D0A:0050 4003A8C0:E04D 03 ...   # 03 = SYN_RECV, 10.77.0.2:80 <- 192.168.3.64
```

老连接为什么还活着:**Linux 在 connect/accept 时把路由缓存进了 socket 的
dst entry**, 之后路由表怎么变都不影响它。所以"已有的能用、新的全死"。

**第二层 (更隐蔽, 是真正的元凶): `learn_peer()` 的自锁。** 代码本来就有
逐对端 `/32` 主机路由的设计 (`/32` 比 `/24` 更具体, 一定胜出), 但:

```python
if src in self.lan_peers:
    self.lan_peers[src] = now
    return                       # <- 相信内存字典, 不重新下发
```

`lan_peers` 是**内存字典, 它不反映内核路由表**。启动时的 DHCP 客户端
(`eth0` 的 udhcpc 助手脚本会 `ip route flush`) 把 `/32` 冲掉之后,
`lan_peers` 里那条记录还在 —— 于是 `learn_peer()` 永远提前返回, **再也不补**。
实测: 从 192.168.3.64 收到 853 个包, 路由表里却一个 `/32` 都没有。

### 修法

```python
elif now - seen < PEER_REASSERT:   # 5 秒
    return                          # 注意: 这里**不刷新**时间戳
...
self.lan_peers[src] = now
_sh([IP_CMD, "route", "replace", src + "/32", "dev", TUN_NAME])
```

两个要点:

1. **定时重新下发, 不是"记住就行"**。时间戳记的是"上次真正下发路由的时刻",
   所以早退分支**不能**刷新它 —— 这一点我第一版写错了: 因为每个包都会走早退
   分支, `now - seen` 永远 < 5s, 重新下发成了死代码, 路由依然补不回来。
2. 顺带加了 `is_lan_addr()` 过滤: 板子默认路由是隧道, 所以**公网回包也从隧道
   进来**, 它们的源地址 (实测 `119.28.183.184`) 被当成"对端"学走一个
   `/32`, 白白占用 16 个名额之一。公网地址不可能与本机直连子网冲突, 不需要
   `/32`。

### 验证

```
清掉 /32 -> 连接 8888 -> 仍在 1 秒内建立 (1049ms 那次就是重新学习+重试)
-> 路由自动回来, 后续连接稳定 18~32ms
```

### 运维结论 (重要)

**调试网线和 WiFi 在同一个网段时, 板子的 `eth0` 地址必须让位于隧道。**
`/32` 学习机制会自动做到这一点 (这正是它存在的意义), 代价是:
浏览器在用时, 板子的 `192.168.3.88` 直连 SSH 会被让位 —— 浏览器静默
120s (`peer_idle`) 后路由被撤回, 网线通道自动恢复。这是**设计如此**,
不是 bug。要调试时优先用 USB ADB。

## 3. 第三成因: 空闲轮询退避吃掉了空闲 RTT

板子是 SPI 主机, **C5 那边排队的包只有等板子下一次时钟才会被取走**。
所以退避 = 直接加到控制延迟上, 而且每个往返要加两次 (请求进 + 回复出)。

原实现是 1ms → 4ms → 8ms 的阶梯, 空载实测掉到 ~110 帧/s:

```
每帧 = 8ms 睡 + 2.1ms 时钟  =>  空闲往返 ≈ 2 x 10ms = 20ms
```

但裸 spidev 实测 (`_spi_bench.py`, 400 帧 20MHz):

```
理论线时:        1.638 ms
实测 min:        1.825 ms   (开销 0.187ms)
实测 p50:        2.128 ms   -> 470 帧/s 可达
```

**也就是说 9.1ms 里只有 2.1ms 是硬件, 剩下 7ms 纯是睡眠。** 改成
0.5 / 1 / 2ms 阶梯 (封顶 2ms) 后空闲帧率 110 → 265 帧/s, 空闲 RTT
25.0 → 21.0ms。

保留退避的原因: 一个 4096B 帧不管多空都是 1.64ms 线时, 全速轮询会让
单核 A7 长期烧掉可观 CPU。封顶 2ms 约等于原来空闲 CPU 的 1/3。
**图传在流时 outbox 永不为空, 这个分支根本不走**, 全速运行。

## 4. 顺带加的观测: 队列深度

`ip_txq` 是 128 个包 (`maxlen=128`), 按 1352B/包算约 **173KB**。
若真的堆积, 在 ~970KB/s 的隧道上就是 **180ms 的缓冲延迟** —— 又一个
潜在的 200ms 来源, 所以必须能看见它。

pump 日志行现在带上了队列深度:

```
[pump] t=2151.2s  227 frames/s, 191.0 KB/s up
       (fails=0, retx=0, ip tx=5537 rx=1443 drop=0 q=0/128 hi=0)
```

实测 (720p 图传 190KB/s 在流): **`q=0/128`, `drop=0`** —— 队列根本没积压。
隧道容量 ~970KB/s, 视频名义 ~190KB/s, 约 5 倍余量。所以**不需要缩短队列**,
这也排除"缓冲膨胀"这条嫌疑。

## 5. 排查过程中被排除的嫌疑

| 嫌疑 | 结论 | 证据 |
|---|---|---|
| SPI 时钟太高 | **排除** | 20MHz 下 `fails=0`, 线时 1.64ms; 24MHz 才不可靠 |
| 编码器 GOP / B 帧 | **排除** | `gop_mode = normalP` (无 B 帧, 无重排延迟), `gop=12` |
| 码率太高 | **排除** | 190KB/s 对 970KB/s 容量, 5 倍余量; 且用户明确要求不降画质 |
| 队列缓冲膨胀 | **排除** | 实测 `q=0/128` |
| CPU 打满 | **部分** | 单核上 spinet+mediamtx+rkipc 争抢, 帧率 470→240; 这是下一节的方向 |
| 隧道丢包 | **排除** | `fails=0 retx=0` 全程 |

## 6. 还能再降的空间 (未做, 按性价比排序)

1. **内核模块 `spitun.ko`**: 现在帧率 240/s 而裸 SPI 可达 470/s, 差的
   ~2.1ms/次 全是用户态 Python + 单核争抢。内核模块没有这层开销, 是
   把隧道 RTT 从 ~20ms 压到 ~10ms 的正路。但它的数据面仍坏着
   (`xmit len=0`), 是遗留问题。
2. **减小 SPI 帧长** (4096 → 2048): 每次交换线时 1.64 → 0.82ms, 一个往返
   省 ~1.6ms。**需要 C5 固件同步改**, 且 TUN_MTU 要重算
   (1350 是按"3 个包塞进 4080"选的)。
3. **C5 加一根 "有数据待取" GPIO**: 空闲时板子就能长睡, 有包立刻中断唤醒 ——
   同时拿到"空闲零 CPU"和"零轮询延迟"。需要硬件改动。
4. `input_buffer_count = 2` (rkipc VENC 输入缓冲) 在 30fps 下约 2 帧
   ≈ 66ms。属 Rockchip 标准配置, 调它有掉帧风险, 没动。
