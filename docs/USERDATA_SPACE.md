## 附：`/userdata` 只有 2.2MB —— 写满了会静默失败

排查界面改动"部署了但页面没变"时发现的：`/userdata` 是 **2.2MB 的 UBI 卷**，
当时 **100% 占满（可用 4KB）**。

### 症状（很有欺骗性）

`scp` 上传**成功**（文件确实出现在板子上），但紧接着的 `cp`/`mv` **静默失败** ——
于是 `index.html` 还是旧的，页面刷新后毫无变化，看起来像"改了没生效"。
第一次甚至误判成 `scp` 失败（实际是 `fsetstat` 报权限失败，与传输无关）。

**排查时别只看"文件传上去了没有"，一定要看 `df`：**

```sh
df -h /userdata
```

### 当时占空间的都是什么

| 占用 | 大小 | 说明 |
|---|---|---|
| `cmd_trace.log` | 1.16 MB | 排查控制丢包时开的指令追踪日志 |
| `_snap_kernel/` | 1.4 MB | 内核状态快照（历史备份，含已废弃的 `S99rtcinit`/`gps_tz.py`）|
| `spitun_new.ko` / `spitun_prev.ko` | 各 354 KB | 内核模块备份（`spitun_new.ko` 与正在运行的 **md5 完全相同**，纯冗余）|
| `car/*.bak*`、`_bak_ui.html` 等 | ~240 KB | 前端历史备份 |
| `car/__pycache__/` | 284 KB | Python 字节码（自动重建）|

### 清理原则

1. **先备份再删**：`tar` 整个打走存到 PC，确认能解开、关键文件都在，再动手。
   （对应 `board_userdata_backup_*.tar`）
2. **删之前先比 md5**：确认"备份的 ko"和"正在跑的 ko"是不是同一个 —— 是就放心删。
3. **顺手关掉日志源**：删 `cmd_trace.log` 的同时删掉 `/userdata/cmd_trace_on`，
   否则它随时又长回来。
4. `__pycache__` / `.bak` 可以放心删。

清理后：**可用 4KB → 1.9MB（100% → 17%）**。

> 教训：这块板子的 `/userdata` 小到**一次日志就能写满**。任何"部署到板子"
> 的操作，都该先看 `df`，并且把结果当成部署是否成功的判据之一 ——
> 只看文件传没传上去是不够的。
