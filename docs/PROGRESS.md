# 无线图传/遥控 稳定低延迟 — 进度追踪

> 目标：**无线（无网线）下，图传 + 遥控稳定、延迟低。**
> 原则：**删代码优于加代码**；优化优先，代码简洁高效。
> 最近更新：内核 TUN 架构落地 → 应用层代理全部删除 → 460 次压测零失败。
> 历史排查细节见 `docs/ISSUES.md`；本文档只保留**当前有效**的信息。

## 一、架构（已更换，这是本轮最大变化）

```
[浏览器 192.168.3.64]
        |  WiFi
        v
[ESP32-C3  192.168.3.69]                 <- WiFi station
   |  spi0 10.77.0.1  ^
   |                  | NAPT（源地址改写）+ 5 条端口映射
   v                  |
[SPI 隧道：裸 IP 报文，一帧一包，MTU 1400]
   |                  ^
   v                  |
[Luckfox 板子  tun0 10.77.0.2]           <- 真正的网络接口
        |
        +-- web_server :80          标准 TCP
        +-- sshd       :22          标准 TCP
        +-- mediamtx   :8889 WHEP / :8189 ICE-UDP + ICE-TCP
        +-- rkipc      :554  RTSP 源
```

板子是一个**真正的一等局域网主机**：有 IP、有路由、有完整 TCP/UDP 栈。
浏览器连的是板子的真实 socket，中间没有任何人重建连接。

### 曾经被迫绕的远路（现已全部删除）

板子内核原本没编 `CONFIG_TUN`，所以**无法拥有 IP 地址**。为了无网线时还能访问
板子，只能在用户态把每条 TCP 连接重建一遍：C3 跑反向代理 accept 浏览器连接 →
通过 SPI 发 `APP_REVOPEN` → 板子去连 `127.0.0.1:<port>` → 两端逐字节搬数据，
连接状态记在 C3 的"槽位表"里，**最多 8 条并发**。

这套东西是所有不稳定现象的根源：无 UDP（WebRTC 媒体只能用 TCP，延迟高）、
并发上限 8、无重传、槽位泄漏、`REVOK` 时序问题、C3 的 150KB 堆吃紧，
外加一整套给板子自己用的 HTTP/SOCKS5/DNS 用户态代理。

**`tun.ko` 补上了缺失的那一半，上面这些全部成了死代码。**

## 二、✅ 已完成（全部有实测证据）

### 1. 内核 TUN 模块 —— 无需重刷内核

- 板子内核 `5.10.160`，`vermagic=5.10.160 mod_unload ARMv7 thumb2 p2v8`
- 云端交叉编译出 `tun.ko`（688,676 字节，无外部依赖）
- 持久化在 `/oem/usr/ko/tun.ko`（ubi4_0，20MB 分区），由 `S14tun` 开机加载
- `S14tun` 兜底 `mknod /dev/net/tun c 10 200`，不依赖不可控的 udev 规则
- **零风险**：纯模块，不动 `boot.img`，不重刷内核

> **踩坑**：`config TUN` 被包在 `drivers/net/Kconfig` 的 `if NET_CORE` 里，
> 而原配置是 `# CONFIG_NET_CORE is not set` → **Kconfig 符号不可见**。
> `CONFIG_TUN=m` 无论怎么写都会被 `olddefconfig` 丢弃、也不会出现在 `auto.conf`。
> 必须先 `--enable NET_CORE`，再 `--module TUN`。

### 2. C3 侧 spi0 网卡 + NAPT + 端口映射

`firmware/c5-tunnel/spinet.{c,h}`（约 230 行）：

- 纯点对点 lwIP 网卡 `spi0 = 10.77.0.1/24`，无以太头、无 ARP
- **`napt` 标志打在 spi0（LAN 侧）上** —— ESP-IDF NAPT 的关键约定，
  打反了源地址不会被改写，局域网根本没有回 `10.77.0.2` 的路由
- `ip_portmap_add` 注册 5 条映射（目标 `10.77.0.2`，maddr `192.168.3.69`）：

  | 协议 | 端口 | 用途 |
  |---|---|---|
  | TCP | 80 | web 控制页 |
  | TCP | 22 | SSH（没网线时唯一的登录途径）|
  | TCP | 8889 | WHEP 信令 |
  | TCP | 8189 | ICE-TCP 回退 |
  | UDP | 8189 | **WebRTC 媒体（低延迟路径）** |

- IP 报文走**独立队列** `s_ipq`（深度 16），优先级高于其它载荷 ——
  控制指令不能被 4000 字节的视频分段堵在后面

### 3. 板子侧 TUN 收发通路

`car/spinet.py`：`TunDev` 类 + 帧类型 `T_IP = 0x05`

- 用 `ioctl(TUNSETIFF)` 建 tun0（BusyBox 的 `ip` **不支持 `tuntap` 子命令**）
- pump 循环每轮最多取 4 个包，避免一段突发独占 pump

### 7. 自愈机制（这套东西现在很难再"假死"）

- **`tun0` 地址自愈**：见 bug 4。开机后实测 **`vanished` 计数 = 0**
- **对端路由自愈 + 120 秒过期**：见 bug 5
- **默认路由跟随网线**（两个独立触发条件，缺一不可）：
  - (a) `carrier` 消失：Linux 在**载波丢失**时不会删除 IPv4 路由，拔线后
    `default via 192.168.3.1 dev eth0` 仍在表里，所有出网包被投进死链路。
    但部分 PHY 在没插线时仍报 `carrier=1`，所以不能只靠这个。
  - (b) **表里根本没有默认路由**：无歧义，覆盖"别的东西把 eth0 路由删了"的情况。
  - 网线回来时再把默认路由交还 eth0。每 30 秒检查一次（一次 fork）。
- **`S99yy_spinet_wd`**：进程死亡或 `/tmp/c3_state.json` 变旧（>5 秒）即重启隧道

> **定位**：网线**只是调试用的 SSH 通道**，产品功能一律不依赖它。
> 上面这套逻辑的目的就是"拔了线也照常上网"，实测已验证。

## 三、本轮修掉的 5 个真 bug（每个都有实测证据）

### 1. `pbuf_alloc(PBUF_RAW, ...)` 不预留链路层头部

`PBUF_RAW` 的 offset 是 0，**没有头部空间**。转发时 `ethernet_output()` 第一句
就是 `pbuf_add_header(p, SIZEOF_ETH_HDR)`，没空间直接 `ERR_BUF` 丢弃。

症状极具误导性：C3 **收得到**板子发的每个包（`ip rx` 一路涨）、
ping 自己的地址也通（本地投递不需要以太头），但**所有需要转发的包全部静默消失**。
实测 `ip rx=400 / ip tx=6`。改用 `PBUF_LINK`。

### 2. 在 /24 上设置 `NETIF_FLAG_BROADCAST`

点对点链路**没有广播地址**。打开这个标志后：

```c
ip4_addr_isbroadcast(10.77.0.2, spi0)
  = ip4_addr_netcmp(10.77.0.2, 10.77.0.1, 255.255.255.0)  // 同网段 -> true
    && !ip4_addr_cmp(10.77.0.2, 10.77.0.1)                // 主机位不同 -> true
```

而 `ip4_input` 找目的网卡的循环**会遍历所有网卡**（源码里是 `NETIF_FOREACH`），
于是每个发往 10.77.0.2 的入站包都被判成"C3 自己的广播"，
`netif != NULL` → **不进转发分支** → 本地投递 → 没有 socket → 静默丢弃。

### 3. 端口映射的目标地址写成了 C3 自己

```c
IP4_ADDR(&ip, 10, 77, 0, 1);              // C3 自己
uint32_t board = ip4_addr_get_u32(&ip);   // 注释写着 .2，拿到的却是 .1  ← BUG
```

每个入站连接都被改写目的地到 `10.77.0.1:80`，而 `ip4_input_accept()` 一看
"目的 == 本机地址"就本地投递 —— **无论广播标志是否移除都不会转发**。
这就是为什么修完 bug 2 之后入站依然不通。

### 4. `rkipc` 反复执行 `udhcpc -i tun0` 清空接口

- 现象：地址在启动自检时还好，几秒后就没了，且**反复发生**
- 定位：监视进程表，抓到 `udhcpc -i tun0 -T 1 -A 0 -b -q`，**父进程是 init(1)**
  （启动者已退出，udhcpc 用 `-b` 自己转后台后重挂到 init）
- 启动者：**`rkipc`**（Rockchip 摄像头程序，二进制里含该选项串）
- 机制：tun0 是点对点链路，永远没有 DHCP 服务器；`-T 1` 一秒超时后**无限重试**，
  每一轮都调用 `/usr/share/udhcpc/default.script` 的 `deconfig` 分支，而它开头就是
  `ip addr flush` + `ip route flush`
- 修复：在该脚本开头插入 tun0 短路保护（`[ "$interface" = "tun0" ] && exit 0`），
  从**伤害源头**掐掉，不去改无法修改的二进制
- 结果：`vanished` 自愈计数从反复触发变成 **0**

> **教训**：`ip addr add` 在这块板子上**返回 0 却不一定生效**。
> 永远回读校验，不要相信返回码。

### 5. 非对称路由（多宿主机的经典陷阱）

板子同时有 eth0（调试网线 `192.168.3.68/24`）和 tun0（真链路）。
浏览器从隧道进来，板子回包目的地是 `192.168.3.64`，
而主路由表 `192.168.3.0/24 dev eth0` → **回包从网线出去**、源地址 `10.77.0.2`；
PC 当初连的是 `192.168.3.69`，收到来自 `10.77.0.2` 的应答直接丢弃 → 一直超时。

实测：8 次连接让板子 `ip rx` 涨 **84**，而 `ip tx` **一个都没涨**。

内核**没编策略路由**（`ip rule` 报 `Operation not supported`），
BusyBox 的 `ip` 也不支持 `table` 参数。替代方案：
**给每个从隧道进来的真实对端自动加一条 /32 主机路由**（比 /24 更具体，一定赢），
地址从流量里学来，不硬编码任何主机。对端静默 120 秒即撤销该路由。

### 6. BusyBox 的 `ip route show default` **不过滤**

```sh
# ip route show default
10.77.0.0/24 dev tun0 scope link  src 10.77.0.2
172.32.0.0/16 dev usb0 scope link  src 172.32.0.70
192.168.3.64 dev tun0 scope link
```

**它把整张路由表全打出来了** —— "default" 被当成路由匹配式解析，而不是过滤器。
于是"输出为空就说明没有默认路由"这个判断**永远为假**：

- `configure()` 永远认为"eth0 还有默认路由"，**从不安装 tun0 的默认路由**
- 这正是"拔了网线也能上网"这条需求的关键路径 —— 拔线后板子直接失去默认路由，
  表现是 `ping: sendto: Network is unreachable`

改法：自己解析完整路由表，只取以 `default` 开头的行。

> **教训**：BusyBox 的工具是精简实现，`ip` 的参数语义和 iproute2 **不完全一致**。
> 关键判断不要依赖它的输出过滤，自己解析。

### 7. 🔴 开机加载顺序错误 —— 重启后整个无线路由全部失效

**现象**：用户重启板子后，`http://192.168.3.69/` 打不开（无线彻底不可用），
但网线 `.68` 的 HTTP 200 一切正常。

**双重根因**：

**(a) `S14tun` 跑在 `S20linkmount` 之前。**
`tun.ko` 放在 `/oem/usr/ko/`，而 `/oem` 是**独立 ubi 分区，由 `S20linkmount` 挂载**。
所以 `S14tun` 执行时那个 `.ko` 根本不存在，`insmod` 失败。
它只来得及建出 `/dev/net/tun`（在 rootfs 上）—— **设备节点存在、模块却没加载**，
这个组合极具迷惑性。

修复：改名为 **`S21tun`**（排在 `S20linkmount` 之后），并**循环等待 30 秒**等 `.ko` 出现，
这样以后挂载顺序再变也不会静默失效。

**(b) spinet 在 tun0 不可用时会 `return 1` 直接退出。**
这是**我自己引入的回归**：tun0 是板子**唯一**的网络通路，一个模块加载失败就把
整条无线链路彻底打死，而硬件其实完好。日志显示它被重启了 4 次，每次都同样退出。

修复：改为**不退出**。SPI 链路继续跑，`housekeeping()` 每 30 秒重试建接口，
成功后无线通路自动恢复。另外 spinet 自己也会尝试 `insmod` 兜底。

### 8. 竞态：`try_setup_tun()` 被两个线程同时调用

修完 (b) 之后立刻踩到：`try_setup_tun()` 同时被 `main()` 和 pump 线程的
`housekeeping()` 调用，两个线程各开一次 `/dev/net/tun`：

```
/proc/2897/fd/4 -> /dev/net/tun
/proc/2897/fd/9 -> /dev/net/tun     ← 两个 fd
[Errno 16] Device or resource busy
AttributeError: 'NoneType' object has no attribute 'configure'
```

线程 A 抢到 `tun0` 名字，线程 B 的 `TUNSETIFF` 报 `EBUSY`，进了 `except` 之后
**把 `self.tun = None`，覆盖掉 A 已经成功的对象**；A 接着调 `self.tun.configure()`
就崩了。结果 `tun0` 建出来了却**没有地址、MTU 还是 1500**，隧道自然不通。

修复：加 `threading.Lock`，并且**只在接口完全配好之后才发布 `self.tun`**，
让并发调用者永远看不到半成品；`TunDev` 构造失败时关掉 fd（原来会泄漏）。

### 9. pump 线程必须在自检之前启动

原版是「先启动 pump 线程 → 再自检」，我在重写时改成了「先自检 → 再启动 pump」。
而自检要 ping `10.77.0.1`，**这个 ping 必须靠 pump 搬运 SPI 帧** ——
所以自检必然失败，还在日志里留下假的 `TUN link is down`，并且把隧道的可用时间
推迟了整整一个重试循环。

修复：pump 线程最先启动（它内部已经能容忍 tun0 还不存在）。

### 4. 提醒：网线插着时 `.68` 会被遮蔽

## 七点五、2026-09-25 第二轮：启动时间、图传重连、看门狗误杀

### A. 🔴 图传无限重连 —— **`lo` 没有 IP 地址**

**现象**：浏览器信令连得上（8889 `ESTABLISHED`），但一直重连；mediamtx 日志：

```
ERR [path car] [RTSP source] dial tcp 127.0.0.1:554: i/o timeout
INF [WebRTC] [session ...] closed: no one is publishing to path 'car'
```

**根因**：`lo` 只有 `UP` 标志却**没有 127.0.0.1**，内核因此没有
`local 127.0.0.1` 路由：

```
ip route get 127.0.0.1  →  127.0.0.1 via 10.77.0.1 dev tun0  src 10.77.0.2
```

**所有本机连接都被当成外网流量从隧道发出去了**，mediamtx 自然连不上 rkipc。
从外部连 8889 反而是好的 —— 这一点让问题看起来像"图传故障"而不是网络故障。

**为什么是我造成的**：spinet 现在 t≈2.4s 启动（原来 t≈16s），**早于 `S40network`
的 `/sbin/ifup -a`**。spinet 抢先把默认路由装上了，busybox 的 `ifup` 随后判定
`interface lo already configured`（它只看自己的状态文件）就跳过了，loopback 从没配上。

**修复（两处，故意冗余）**：
1. 新增 `S15loopback`，开机早期直接断言 `127.0.0.1/8`，不依赖 `ifup`
2. spinet 的 `housekeeping()` 用 `bind()` 零开销地检测并自动补回

### B. 🔴 看门狗一直在**误杀健康隧道**（长期不稳定的重要来源）

`state_age()` 两个缺陷：

```
Sat Jan  2 01:20:37 UTC 2021  tunnel WEDGED (no status for 99999s) -> restarting
Fri Sep 25 11:06:18 UTC 2026  tunnel WEDGED (no status for 28800s) -> restarting
```

1. **文件不存在时返回 99999** → 开机时 `/tmp` 是 tmpfs，状态文件还没生成，
   看门狗**立刻判卡死并重启**，把刚起来的隧道又拆掉
2. **用墙上时钟算年龄** → 板子 RTC 是错的（`Jan 2 2021`），时钟任何跳动都会
   把"刚写的文件"算成几小时没更新 → 又误判

**每次误判 = 一次无谓的隧道拆除重建（数秒中断）**，这正是"老是不稳定"的来源之一。

**修复**：文件缺失只在连续 20 次（约 60 秒）后才当回事；年龄不合理
（负数或 > 1 小时）视为时钟跳变，重置基准而不是判定卡死；进程存活检查保持严格不变。

### C. ⚡ 启动优化：32.1s → 21.6s（省 33%）

> **定位**：网线**只是调试用的 SSH 通道**，产品永远无线运行。下面所有优化都以
> "拔掉网线"为前提。

**最终分解**（每一步都有实测）：

| 阶段 | 原来 | 现在 |
|---|---|---|
| 关机（rcK stop 阶段）| 7.76s | **3.74s** |
| u-boot | ~4.7s | ~4.4s（未动）|
| 内核 + init 脚本 | 15.3s | **8.17s** |
| SPI 主从重新对齐 | ~3s | ~3s（未解决）|
| spinet 启动时刻 | t=16s | **t=5.13s** |
| tun0 就绪 | uptime 14.3s | **uptime 8.6s** |
| **开机 → 页面可用** | **32.1s** | **21.6s** |

**做了六件事**：

1. **`S99z_spinet` → `S22spinet`**：它原来排在几乎最后，而依赖
   （`/dev/spidev0.0`、`/dev/net/tun`）早就就绪
2. **`S99web` → `S23web`，删掉 6 秒阻塞 sleep**：原脚本 `sleep 2` + `sleep 4`
   纯粹为了"验证"，没人消费结果；而且它执行 **`killall -q python3`**，
   在 spinet 提前之后会**把隧道一起杀掉**
3. **C3 固件：SPI 从机先武装，再等 WiFi**。原来 `wifi_wait(20000)` 在
   `spi_slave_init()` 之前 —— 板子开机就在等 SPI 握手，而 C3 卡在等 WiFi。
   两者本就无关。改后握手从十几秒降到 **0.2~2.2 秒**
4. **`S99luckfoxconfigload` 改为等 tun0 建好再跑**（见下面的教训）
5. **关机优化**：`S21appinit` 原来等 rkipc 自己退出（5.17s）；反正要重启，
   先 `killall -9 rkipc` 让厂商脚本的轮询立刻通过 → 5.17s **→ 2.13s**。
   另删掉 `S22spinet stop()` 里 1 秒的 `sleep`
6. **整条链前移**：`S50usbdevice` → `S20usbdevice`，于是
   `S21hwcfg`（overlay → spidev）、`S22spinet` 全都提前约 4 秒。
   **关键是保持 `usbdevice` 在 `hwcfg` 之前**（见下面的教训）

**踩到的坑（都已修）**：

- **`S96hwcfg` → `S21hwcfg` 单独提前是个错误**：该脚本把设备树 overlay 写进
  `/sys/kernel/config/device-tree/overlays`，而 **configfs 是 `S50usbdevice` 挂载的**。
  提前之后 `mkdir`/`cat` 静默失败，`/dev/spidev0.0` 再也不出现。
  **正解是把 usbdevice 也一起提前**，保持相对顺序。
- **init 脚本串行且阻塞**：`S22spinet` 曾等 spidev 25 秒，而创建 spidev 的脚本
  排在它后面 —— **死锁**，永远解不开
- **"后台化 ≠ 不占 CPU"**：把 `luckfox-config`（5.94s CPU）改成后台，只是让 init
  不再阻塞它，**单核上它照样把 spinet 饿死** —— 实测 tun0 仍在 uptime 14.3s。
  改成"等 tun0 出现后再跑"才真正解决
- **测量陷阱**：下完 `reboot` 立刻轮询会有**假阳性** —— 板子还会继续服务一两秒。
  必须先等它真的断开再计时。另外要给日志**打上 uptime 时间戳**，
  否则"tun0 何时就绪"和"数据何时真正流通"完全分不清

### D. ⏳ 剩余优化空间

| 项 | 耗时 | 说明 |
|---|---|---|
| SPI 主从重新对齐 | **~3s** | 板子重启后 `fails` 从 36 冲到 255 才稳定。需要改 C3 固件让从机检测主机重启，有风险 |
| u-boot | ~4.4s | 需要动 bootloader（`bootdelay`、内核加载），**有变砖风险** |
| `S20usbdevice` + `S21hwcfg` | 2.8s | `hwcfg` 的 overlay 是 spidev 的前提，动不了；`usbdevice` 要挂 configfs |
| 关机 3.7s | — | **只影响 `reboot`，冷启动（上电）没有这个阶段** |

> **对你实际的用法（上车通电）**：冷启动没有关机阶段，约 **18 秒**可用。

### C. 🔴 第二个真 bug：扫描/重连互相死锁（我写的）

- 扫描期间置位，断开事件处理函数**不再重连**

## 九、2026-10-02 第三轮：控制延迟根因（**不是信号问题，是代码**）

### A. 🔴 头号元凶：HTTP 处理器没关 Nagle → 每条指令白付 36ms

**现象**：控制延迟高，但无线信号正常、SPI 帧率正常、丢包正常。

**定位方法**——在板子上同时起三个对照服务器，用**复用连接**（keep-alive，
浏览器同款）各打 40 次：

| 服务器 | 中位延迟 |
|---|---|
| `http.server` 默认（**就是 `web_server.py` 原来的样子**）| **49.99 ms** |
| `http.server` + `disable_nagle_algorithm = True` | **13.89 ms** |
| 裸 socket，整个响应一次 `send()` | **5.79 ms** |

真 `web_server.py` 实测：`/api/ping` 49.98 / `/api/status` 50.31 /
`/api/move` 50.52 / `/api/cmd` 50.46 —— **每个端点都是 50ms，
包括完全不碰电机代码的 `/api/ping`**。固定开销，与业务无关。

**根因**：响应分两次 `write` 发出（`send_response` 的头部一次、body 一次）。
浏览器保持长连接，第一个小包发完后 **Nagle** 要等对端的延迟 ACK，而对端此刻
没有数据要回，得等自己的延迟 ACK 定时器（Linux 40ms）。于是每条指令白白多付
约 36ms。**跟无线、SPI 速度、信号强度全无关系。**

**修复（一行）**：

```python
class H(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    timeout = 15
    disable_nagle_algorithm = True   # socketserver.StreamRequestHandler 官方开关
```

**关键测量陷阱**：**每次新建连接测不出这个问题**——我第一轮就是新建连接测的，
看到"Nagle 开关无差别（20.2 vs 21.2ms）"，于是**误判成与 Nagle 无关，走了弯路**。
必须**复用连接**测。浏览器用的正是复用连接。

**效果**（板子本机，复用连接）：49.98ms → **13.89ms**；
端到端（电脑→无线→C5→SPI→板子）：中位 **23~32ms、最差 ≤118ms**
（改前最差 485~2388ms）。

### B. 🔴 第二个代码问题：SPI 每次交换都搬满 4096 字节（尚未修）

`spinet.py` 的 `exchange()`：

```python
tr = struct.pack("<QQIIHBBI",
                 txaddr, ctypes.addressof(self.rxbuf),
                 FRAME, self.speed, 0, 8, 0, 0)   # ← len 恒为 FRAME(4096)
```

`len = FRAME` 意味着**每次交换都在线上走满 4096 字节**，包括完全空的
`T_NODATA` 心跳探测。20MHz 下 = **1.64ms 纯线上时间**，与载荷大小无关。

后果（实测）：
- 隧道往返 **11ms**（板子 ping `10.77.0.1`），其中大部分是这段死时间
- 每次交换 3.8ms → 只有 **264 帧/s**
- 每秒搬 `264 × 4096 = 1.08 MB` 的 SPI，只为送 **45 KB** 数据 → **96% 是浪费**
- spinet 泵线程 **占单核 25%**（`tid=602`，全板第一大 CPU 消耗）

> 注意：老版本注释写的"只写头+载荷"指的是**避免在 Python 侧把 4KB 清零**
> （`ctypes.memmove` 只写 HDR+len），**不是**减少线上字节数。线上依然是 4096。
> 帧率 154→395 是省掉了 Python 侧开销，**线上时间一点没变。**

**为什么不能直接把 len 调小**：从机→主机的方向，从机最多会发 `FRAME-HDR`
字节；主机只 gated 少数字节就会**截断从机的大帧** → 校验失败 → 丢帧 → TCP 重传。
**必须两边（C5 固件 + spinet）一起改**，且 `FRAME` 不能小于
`HDR + 2 + MTU = 16 + 2 + 1350 = 1368`。取 `FRAME=1408` 可把每次交换的线上
时间从 1.64ms 降到 **0.56ms（2.9×）**，隧道往返有望 11ms → ~4ms。

**代价**：要重新烧 C5 固件（要接 USB）。**有风险，未动。**

### C. 🔴 C5 会被连接churn打垮（**我的压测造成的，不是bug但要知道**）

压测时大量**新建连接**（每个连接 C5 要占一个反向代理槽 + 18KB 缓冲），
把 C5 打进了拥塞崩溃：`.69` 掉到 **90~100% 丢包**，冷置 150 秒**不自愈**，
最后靠断电才恢复。ARP 仍能解析（`d0-cf-13-e5-12-94`），说明 WiFi 驱动还活着，
是转发/堆栈层面崩了。

崩的期间 C5 自报 `log_drop=4209` vs `log_sent=632`（丢 87% 日志），
但 `free=120448`、`minfree=4436`、`largest=94208` —— **堆没耗尽，是拥塞不是 OOM**。

**结论**：前端"同时只允许一个请求在途 + 合并最新状态"（已部署）不只是省延迟，
**它本身就是防止 C5 崩溃的保护**。以后的压测一律**单条连接**打，
不要新建连接churn。

### D. ⚠️ `.68`（调试网线）为什么连不上 —— 已知取舍，可改进

板子路由表：

```
default via 192.168.3.1 dev eth0
192.168.3.64 dev tun0 scope link      ← 学到的主机路由
192.168.3.0/24 dev eth0 scope link  src 192.168.3.68
```

板子学到"PC 的 IP走 tun0"这条 `/32`，于是**回程走隧道**，PC 到 `.68` 的连接
被自己丢掉。现在表现：`.68` **能 ping 通但没有任何 TCP 端口开放**（22/80/554/8889 全 False）。

文档里把它当"必要取舍"，但**其实不必**：只有当"现有路由到不了该地址"时才该加
这条 `/32`。PC 本来就在 `192.168.3.0/24` 里，回程走 eth0 → 路由器也能回到 PC。
**这是个值得修的真问题**（修了调试网线就恢复可用）。未动。

### E. 测到的其它事实（供后续判断）

- `spi_speed = 20000000` ✅（C5 的 SPI 从机在 40MHz 下必挂，20MHz 稳定）
- `fails = 902` 且在缓慢增长（t=1305s 时 341）→ **约 0.47 次/秒丢帧**，
  这是残余 200ms+ 卡顿的来源（TCP 最小 RTO 200ms）
- `drop = 720` 且**早已冻结**（t=1305s 和 t=2552s 都是 720）→ 队列丢包**不是**当前问题
- `loadavg 11.5`，其中 **10 个 D 状态任务是 RK 视频内核线程**
  （`vlog/valloc/vsys/vrga/venc/rkisp/vpss/vrgn`，`wchan=down`）——正常，但
  它们在单核上有调度压力。**loadavg 在这里主要反映它们，不代表 CPU 真被占满**
- CPU 大户：spinet 泵 25.3%（`wchan=spi_transfer_one_message`）、PWM 线程 10.8%
  （`hrtimer_nanosleep`，4 电机 × 250Hz × 2 次写 = 2000 次 ioctl/s）、
  mediamtx+rkipc 约 29%
- C5 的 `rssi = -65 ~ -66 dBm`（天线坏了那个，能用但不算强）

## 十一、2026-10-03 第五轮：冷启动、GPS 坐标系、摄像头过曝

### A. ⚡ 冷启动：C5 从 15.8s → 1.3s（省 14.5 秒）

**根因是我自己造成的**：为了解决"找不到 AP"的排查问题，我在 C5 固件里加了
开机诊断扫描，而为了能看见 5GHz 的 AP 又改成扫全频段。每个信道等 200ms，
**实测阻塞 11.6 秒**：

```
改之前的 C5 启动日志:
  t= 989ms   wifi sta started
  t=12642ms  SCAN: 扫到 14 个 AP     <-- 11.6 秒全耗在这里
  t=15647ms  wifi:connected
  t=15767ms  got ip
```

**扫描只是诊断手段，不是连网的必要步骤。** 改法：把扫描从开机路径移走。

| | 原来 | 现在 |
|---|---|---|
| 开机顺序 | 先扫描(11.6s) → 再连 | **立刻连** |
| 扫描时机 | 每次开机 | **仅连续断开 30 秒后** |
| 每信道耗时 | 200ms | 90ms |

**改之后的实测**（C5 自己的时间戳，不是秒表）：
```
t= 991ms   wifi sta started
t=1189ms   wifi:connected with HUAWEI-ER15NM_5G_Wi-Fi5
t=1325ms   got ip: 192.168.3.69
```

**板子侧本来就快**：`boot done t=8.78s`（S22spinet t=5.37s、S23web t=5.47s）。
所以整机冷启动 ≈ 板子 8.8s 与 C5 1.3s 并行，**瓶颈已经回到板子侧**。

**顺带修掉一个隐患**：`wifi_scan_report()` 内部会先 `esp_wifi_disconnect()`。
原来 WiFi 只要**短暂**断开就触发扫描，等于**把正在恢复的连接又拆掉**。
现在要求连续 30 秒连不上才扫。

### B. 🔴 GPS 坐标系：百度地图偏 1.3 公里

**现象**：`38.902983, 121.560611`，地图上落点偏离实际位置很多。

**这不是 GPS 不准，是坐标系没换。** GPS 输出 WGS-84，而中国法律要求公开
地图服务用加密后的 GCJ-02，百度再叠一层 BD-09。网页原来直接：

```js
href="https://map.baidu.com/?latlng='+g.lat+','+g.lon+'"   // 拿 WGS 喂百度
```

**少了两步转换**，实测偏移：

| 坐标系 | 坐标 | 相对原始值 |
|---|---|---|
| WGS-84（GPS 原始） | 38.9030, 121.5606 | — |
| GCJ-02（高德/腾讯） | 38.9038, 121.5655 | **441 米** |
| BD-09（百度） | 38.9102, 121.5719 | **1268 米** |

**修法**：转换放在板子的 `web_server.py` 里（`wgs84_to_gcj02` /
`gcj02_to_bd09`），API 同时返回三种坐标。原始 `lat`/`lon` 保持 WGS-84 不动
（数据要干净），网页只拿算好的 `bd_lat`/`gcj_lat` 拼链接。**境外自动跳过
转换**（那套算法只在中国境内有效），并给一个 `in_china` 标志。

顺手加了高德链接 —— 百度地图加载慢、有广告，高德更干净。

### C. 🔴 GPS 解析器三个缺陷

实测抓到的原始 NMEA：

```
$GPTXT,01,01,01,ANTENNA OK*35          <- 天线自检通过, 硬件没问题
$GPGSV,1,1,04,12,,,27,25,,,29,...      <- 看到 4 颗星, 但 C/N0 全是空
$GNGGA,025919.000,,,,,0,00,25.5,...    <- 0 颗可用, 精度因子 25.5
$GNRMC,025918.000,V,,,,,,,031026,,,N,V <- V = 无定位
$GN$GNGGA,025921.000,,,,,0,00,25.5,... <- !! 被污染的语句
```

三个问题，都已修：

1. **没有校验和验证**。串口有帧错误（`dmesg fe:4`），数据流里混进
   `$GN$GNGGA` 这种杂质，会被当成有效定位数据。现在 `_nmea_ok()` 逐条校验，
   丢弃损坏行。
2. **只认 `$GPGGA`/`$GNGGA`**。实际模块混发 GN/GP/BD 三种 talker，而且
   `$GNGLL` 也带经纬度。现在按语句类型（GGA/RMC/GLL/GSV）判断，不依赖前缀。
3. **状态无法区分**。"没接""没星""信号弱""定位中"四种情况在网页上长得
   一模一样，只能靠猜。现在 `gps_state()` 归纳成一句人话：
   ```
   state       weak
   state_text  看到卫星但信号弱 (C/N0 34, 需 >30)
   seen 6913   bad 0        <- 6913 条语句全部校验通过
   ```

**实测结论：室内永远定不了位。** `C/N0 34` 卡在 30 的阈值上，`$GPTXT` 明确报
`ANTENNA OK` —— 硬件没问题，是**看不到足够天空**。GPS 需要 ≥4 颗星且
C/N0 > ~30 才能解星历。**拿到室外朝南开阔处**即可，软件无能为力。
（用户后来在室外拿到 6 星定位。）

`S22spinet` 的 `stop()` 只杀 `spinet.py`，不会误伤 web/sshd；`S24spinet_wd`
看门狗是兜底。**重启后务必确认 PID 变了。**

## 十二、2026-10-03 第六轮：摄像头过曝真因 + 实时滑块

### A. 🔴🔴 真因：默认曝光值太高（`exposure=408`）

**之前所有"调 ISP 参数"的做法都是错的**，包括我在 D 节里记的那一轮。
真正的原因是传感器曝光量本身设得太高：

```
/dev/v4l-subdev2 的可写 v4l2 控制:
    exposure       min=1  max=1624   value=408     <- 默认 408, 太高
    analogue_gain  min=128 max=99614 value=128
```

实测（同一场景，只改 exposure）：

| exposure | 平均亮度 | 最暗 | 对比度 std |
|---|---|---|---|
| 400（默认） | 206.1 | 32 | 59.9 |
| 1200 | 242.4 | 44 | 27.1 |
| **100** | **124.1** | 0 | **58.8** |

`exposure=100` 时画面完全正常：清晰、颜色正确、明暗层次齐全。
对比最初那张"几乎全白"的画面（平均 225、对比度 8.7），这是根本性改善。

**顺带纠正 D 节的一个判断**：`brightness`（ISP 的加法偏移）**不是**正确
的调节手段 —— 改它反而会让 AE 补偿更多，越调越亮。正确手段是改传感器
曝光量。

### B. ⚠️ 最大的教训：改 ISP 参数不要重启 rkipc

**我踩了三次同一个坑**，每次都导致图传黑屏、只能重启板子：

```
bind socket to address failed : Address already in use
```

成因：`kill rkipc` 后旧进程的 RTSP 监听 socket 残留在内核里（实测组件
全停了 `554` 仍有 19~39 条残留条目），新进程 bind 失败 → rkipc 活着但
不出流 → mediamtx 一直重连 → 网页"一直重连中"。**只能靠重启清掉。**

**正确做法：走 `/dev/v4l-subdev2` 的 v4l2 控制** —— 立即生效、不重启
任何进程、不断图传。**这一条应该写死在脑子里：调摄像头先找 v4l2，不要
动 rkipc.ini + 重启。**

另外 `rkipc` **没有守护进程**，杀掉不会自动回来；它也不在 PATH 里，手动
启动要写全路径 + 补 `LD_LIBRARY_PATH=/oem/usr/lib:/usr/lib`。

### C. ✅ 摄像头实时滑块（新增功能）

因为"画面看着对不对"只有人眼能判断，把控制权交给了用户：

| 控件 | 范围 | 说明 |
|---|---|---|
| 曝光滑块 | 1 – 1624 | 拖动即时生效 |
| 增益滑块 | 128 – 99614 | 暗环境用 |

## 十四、2026-10-04 第八轮：时间错 8 小时的**真正根因**

### A. 🔴🔴 核心事实：RTC 里存的是**本地时间**，内核却当 UTC 载入

**同一时刻三个读数，把问题一次说清：**

```
hwclock -r      -> 19:38     <- RTC 原始值 = 本地时间
hwclock -u -r   -> 03:38     <- 把它当本地再转 UTC（多 +8）
date -u         -> 11:38     <- 真实 UTC
```

**所以 RTC 芯片里存的就是本地时间格式的值**（19:38），而：

1. **内核**启动时把这个原始值**当作 UTC** 载入
   → `system UTC = 19:38`（实际 11:38）→ 本地时间变成 03:38 → **整体快 8 小时**

2. **`hwclock -s` 绝对不能用** —— 它按"RTC 是 UTC"的假设去设系统，
   必然多出 8 小时。**必须用 `date -s <RTC原始值>`** 直接设本地时间。

### B. ⚠️ ntpd 是帮凶，不是元凶

一度以为是 ntpd 把时间改坏的（停掉它时间确实稳了），但实测发现：

```
0.pool.ntp.org -> DNS 解析失败
1.pool.ntp.org -> DNS 解析失败
```

**它的 NTP 源根本连不上**，所以既不能纠正错误、也不会自己同步 —— 只是让
错误一直保持着。**已用 `chmod -x /etc/init.d/S49ntp` 禁用它**（源不可达，
白占进程）。

### C. ⚠️ 我自己踩的坑：`date -u -s` 的语义

busybox 的 `date` **把参数按本地时间解释**，所以：

```sh

```

**正确做法**（已验证）：把 TZ 临时设为 UTC0，设完再恢复：

## 十五、2026-10-04 第九轮：时间问题**真正的解**（第三次才彻底搞对）

### A. 🔴🔴 前两次修复为什么失败

**核心矛盾（这次终于说清了）：内核把 RTC 的值当 UTC 读，而 RTC 里存的是本地时间。**

```
RTC = 21:38（本地时间）
   ↓ 内核启动时当 UTC 载入
系统 UTC = 21:38   ← 错！真实 UTC 是 13:38
系统本地 = 05:38   ← 因为 CST-8 又 +8，整体快 8 小时
```

**前两次我做的事**：用 `date -s <RTC原始值>` 把本地时间设成 21:38
—— **当下看起来对了**，但**内核下次启动仍然把 RTC 的 21:38 当 UTC 读**，
又回到 05:38。**治标不治本，所以每次重启都复发。**

而且 `S99rtcinit` 里"相差 <60 秒就不动"的判断有缺陷：本地的 05:38 与
RTC 的 21:38 在时分秒上差 16 小时，脚本每次都判定"不一致"并重复设置，
形成死循环。

### B. ✅ 真正的解法：让 RTC **真的存 UTC**

```
一次性改写：RTC = 13:38（UTC）
   ↓ 内核读它
系统 UTC = 13:38  ✓   系统本地 = 21:38  ✓
```

**改写之后，内核读 RTC 天然正确，不需要任何开机修正。**

```sh
TZ=UTC0 date -s "2026-10-03 13:39:59"   # 设系统时间（参数按 UTC 解释）
hwclock -u -w                            # 把 UTC 写进 RTC
```

### C. 新的 `S99rtcinit` 逻辑

| 情况 | 动作 |
|---|---|
| RTC 无效（年份 <2020） | 用系统 UTC 初始化 RTC |
| **RTC ≈ 系统 UTC** | **什么都不做**（正常状态） |
| RTC ≈ 系统本地时间 | **改写成 UTC**（一次性纠正） |
| 两者都对不上 | 用 RTC(UTC) 重设系统 |

判断同时和"系统 UTC"与"系统本地"比较，用 `diff_sec()` 算差值并处理跨天。

## 十六、2026-10-04 第十轮：电池电压标定曲线

### A. 📊 关键发现：分压比**不是常数**

**分压比从 8.29 单调升到 8.75** —— 确实有曲率。这解释了：

* 代码里写死 `adc_ratio = 8.71`（接近高压端的 8.75），所以**低压端偏高 0.5V**
* **用户最早报的"电压不准 11.69 / 网页 12.2V"就是这个偏差**
* 单个比值无法同时满足两端：用 8.71 低压差 +0.5V，用 8.30 高压差 −0.63V

### B. ✅ 二次标定曲线

```
V = 712.795469286 − 1.82835728943×raw + 0.00119120707926×raw²
```

| raw | 实测V | 曲线 | 残差 | 对比 8.71 |
|---|---|---|---|---|
| 768 | 11.23 | 11.220 | −0.010 | +0.529 → −0.010 |
| 769 | 11.21 | 11.222 | +0.012 | +0.564 → +0.012 |
| 777 | 11.33 | 11.328 | −0.002 | +0.566 → −0.002 |
| 797 | 12.26 | 12.260 | 0.000 | −0.057 → 0.000 |

* 二次拟合 **RMS = 0.008V**，最大残差 0.012V
* 对比：直线拟合 RMS 0.089V —— **曲线比直线好 11 倍**，证明确实有曲率

### C. 实现细节（`web_server.py`）

```python
BAT_COEF = (712.795469286, -1.82835728943, 0.00119120707926)
BAT_RAW_MIN = 700      # 曲线有效区间
BAT_RAW_MAX = 860

def bat_volts(mv):
    raw = mv / ADC_SCALE_MV
    if BAT_RAW_MIN <= raw <= BAT_RAW_MAX:
        a0, a1, a2 = BAT_COEF
        return a0 + a1*raw + a2*raw*raw
    return mv * ADC_RATIO / 1000.0      # 超范围回退比值法
```

**回退是必要的**：曲线只在 raw 700–860 验证过，电池更低压时二次项会外推
出离谱的值（实测 raw=600 时曲线给出 44V）。

### D. ADC 采样率与过采样

**实测能力**：

| 层面 | 速率 |
|---|---|
| sysfs 读取（实际用的） | **约 1580–1680 次/秒** |
| RV1106 SARADC 硬件 | 可达数十 ksps，但**驱动没暴露速率控制** |

驱动只有 `in_voltage0/1_raw` 和 `in_voltage_scale`，**没有
`sampling_frequency` 属性**，所以只能靠软件过采样降噪。

**已把 `ADC_OVERSAMPLE` 从 48 提到 400**：

| 采样数 | 耗时 | 效果 |
|---|---|---|
| 48 | 约 30ms | 噪声跨度 67–122 LSB |
| **400** | **约 250ms** | 噪声降到约 1/2.9 ≈ 42 LSB (0.06V) |

遥测是 1 Hz 刷新，250ms 只占 25% 周期且跑在后台，**不影响控制延迟**。

### E. ⚠️ 测量方法的教训

**错误做法**：用户看万用表 → 打字告诉我 → 我才去读 ADC。
中间隔了几十秒到几分钟，而**电池在这期间电压在变**（放电/静置回弹），
导致 (raw, 电压) 配对错位。

证据：`raw=767 → 12.30V` 与 `raw=768 → 11.23V` —— **同一 ADC 读数对应
相差 1.07V 的真实电压，物理上不可能**。

**教训**：标定必须**同一时刻**配对。读到电压的同时立刻取 raw。

## 十七、2026-10-04 第十一轮：SPI 变长传输 —— **一次失败实验，已全部回退**

### A. ❌ 结论先行：这个优化**不要做**

回到**固定 `TUN_FRAME_SIZE` (4096) 传输**。板上现在的状态就是最终状态，
代码已全部回退并验证恢复。

### B. 当时的动机（数据是真的，结论是错的）

实测证据确实支持"重传机制是死代码"：

| 指标 | 实测值 |
|---|---|
| `retx`（重传次数） | **全程恒为 0**，一次都没执行过 |
| `fails` | 最大 1（启动早期从机未武装那一次） |
| `tx_dropped` / `rx_errors` | 0 |
| 空载 CPU（1080p 图传时） | `python3` 35%，其中 pump 线程 20.3%，idle 32.8% |

推理：SPI 是板级同步总线，每位都由主机时钟打出，没有丢失/乱序/拥塞，
所以重传、滑动窗口、累积 ACK 都在解决不存在的问题。**这个推理本身没错。**

犯的错在后面一步：从"重传是多余的"跳到"顺手把传输长度也改成变长的"。
这是两件独立的事，后半件是一次**真正的协议改动**，而收益只是空载时的
CPU —— 板上本来还有 33% 余量。**用一次掉线风险去换一个不痛的指标。**

### C. 💥 失败原因（设计错误，不是实现 bug）

方案：从机在自己帧头的 `reserved` 字段里预告"下一帧要传多少字节"，
主机完全跟随（单向，避免循环依赖）。

结果：**整条隧道立刻死掉**。C5 串口实测：

```
frames=14336 ... err=404 | ip tx=0 rx=0 drop=0
frames=28672 ... err=694 | ip tx=0 rx=0 drop=0
```

`err` 稳定每秒涨约 1，`ip tx/rx` 恒为 0。板子两条网络全断（`.68` 不通，
`.69` 只有 C5 应答），SSH 卡在 banner exchange。

**根本原因**：`reserved` 只能表达"我这一帧要**回发**多少字节"，
表达不了"我**需要你发给我**多少字节"。从机按自己的**应答**长度设传输
长度，而上行 IP 包有 1350 字节 —— 当从机这一帧的应答只是 16 字节心跳时，
主机就没有足够的传输长度把包发出去：

```python
if ln and HDR + ln > want:
    payload = b""      # ← 数据永远发不出去，永久死锁
```

包堆在 `txq` 里，而队列满后开始静默丢弃。**一个字段承载不了两个方向的
需求**，这是设计错误。SPI 全双工、收发共用时钟，长度是**单一**的，
不能两边各自声明。

正确做法需要**单独的**"主机方向需求"字段（可复用已不用的 `seq`），
从机取两者较大值：

```
transfer = max(HDR + slave_tx_len, master_next_rx_need)
```

### D. ⚠️ 更严重的操作失误：没有退路就动手

**刷 C5 前没有先确认"出错也能救回来"。** 板子没有串口，唯一的恢复通道
就是这条隧道 —— 而隧道正是被刷掉的东西。结果：板子失联，只能靠用户
物理断电。

但有两点让损失可控，值得记住：

1. **板上的 `spinet.py` 从未被改动**（`scp` 在上传前就失败了）。
   所以只需要把 C5 刷回旧固件，主机侧不用动。
2. **`bin/` 下的旧二进制不能用**（2026-09-22，早于当前协议）。
   正确做法是**改回源码再重新编译**，而不是刷一个来历不明的 bin。

**教训**：
* 改动唯一恢复通道前，先确认还有第二条路（串口 / 网线 / SD 卡启动）
* 网线虽然只是调试用，但**在刷机这种操作前应该插上** —— 这正是它存在的意义
* 源码回退要改 `.c` 重新编译，不要猜着刷旧 bin

### C. 根因二：`udhcpc -i tun0` 占用 RTSP 的 554 端口

rkipc（不能改的 Rockchip 二进制）会拉起
`udhcpc -i tun0 -T 1 -A 0 -b -q`。tun0 是点对点，永远没有 DHCP 服务器，
于是它无限重试，而它的发现 socket 会绑到 **0.0.0.0:554** —— 正好是
rkipc RTSP 要用的端口。

后果：rkipc 起得来、编码正常（dmesg 可见 1080p@30），但 **bind 不上 RTSP**，
`DESCRIBE` 超时，mediamtx 收不到流，网页黑屏。

**这个现象和老的"重启 rkipc 后 554 socket 残留"一模一样**，所以被误诊很久
（`video_ctl.py` 里甚至写了"需要重启板子"）。区别：

* socket 残留 → 等内核回收，只能重启
* **udhcpc 占用 → 杀进程即可，不用重启**

验证手段：`/proc/net/tcp` 里 554 的 inode，去 `/proc/*/fd` 找持有者。

### D. 修复过程中我自己造的坑（必须记下来）

**坑 1：把 28ms 的扫描放进泵循环。**

我写的 udhcpc 清理函数，扫 `/proc`（139 项 × 每 fd 一次 `readlink`，
纯 Python，单核 Cortex-A7）实测 **28ms/次**。而泵的一帧预算只有 2–4ms。
把它挂在 `housekeeping()`（在泵里跑、每 5 秒一次）上，等于每 5 秒把 SPI
泵卡死约 10 帧 → C5 收不到状态帧 → 看门狗判定
`tunnel WEDGED` → 重启 spinet → 循环往复。

**28ms 的调用绝不能出现在 2–4ms 预算的循环里。** 现在它跑在独立线程上，
20 秒一次（占单核 0.14%）。

**坑 2：两段式读取 /proc 会张冠李戴。**

`port554_holder()` 原本先读 `/proc/net/tcp` 拿 inode，再回头扫 `/proc/*/fd`
找持有者。两次快照之间 socket 会被回收、PID 会被复用，于是**报出错误的进程名**。
我因此一度以为是 udhcpc，又一度以为是 rkipc，来回反复好几轮。

正确做法：**先建 fd→pid 映射，再拿 inode 去查**，一次成型。

**坑 3：把 `Test-NetConnection` 的 `True` 当成板子活着。**

C5 自己会应答转发端口（22/80），TCP 握手在 C5 协议栈就完成了，
**完全不代表板子活着**。真正的判据是 SSH 能不能过 banner。

### G. 根因三：看门狗会重复启动，两个看门狗互相拆台

`S24spinet_wd` 的 `stop_wd()` **只杀 pidfile 里记的那个 pid**。而
`start_wd()` 每次调用都覆盖 pidfile —— 于是任何一次多余的 `start`
都会泄漏一个永不退出的循环：

```
start -> pidfile=A
start -> pidfile=B   (A 循环仍在跑，但 pidfile 已经指向 B)
stop  -> 只杀 B，A 永远活着
```

两个看门狗同时跑，各自看到"状态文件过期"就调 `S22spinet restart`，
**互相把 tun0（连带 SSH）拆掉**。现象：`ps` 里有两个 `{S24spinet_wd}`，
日志里反复 `tunnel WEDGED -> restarting`。

修复：`stop_wd()` 用 `ps` 扫出所有 `[S]24spinet_wd` 并全部杀掉
（跳过自己 `$$`）。验证：连续调用两次 `start`，第二次正确回
`already running`，进程数保持 1。

**教训：pidfile 只能追踪"最后一个"实例，不能用来回收"所有"实例。
常驻循环的 stop 必须按进程名兜底清扫。**

### B. 🔴 新根因一：`bad_magic` 0.24% —— SPI 从机"未武装空窗"

板子侧 dmesg 每 30 秒采样：

```
frames=108843 fail=255 bad_magic=255 bad_csum=0
frames=200038 fail=477 bad_magic=477 bad_csum=0
```

- `fail == bad_magic` 且 `bad_csum` **恒为 0** → 不是位错（信号完整性），
  而是**整帧全零** = MISO 没人驱动。
- 速率 ≈ **0.93 次/秒**，占 0.24%。
- 这就是 606ms 延迟尖峰的来源：丢一帧 → TCP 重传 → RTO。

**根因**：旧 `spi_slave.c` 虽然设了 `queue_size = 16`，但
`spi_slave_wait_rx()` 每次只 arm **一个** transaction ——
队列里永远只有 1 个，那个 16 完全没起作用。从 `wait_rx` 置
`s_armed = false` 返回到下一次 `arm()` 之间存在空窗，主机撞上就读到零。

**修复**：改成 **SLV_DEPTH = 3 个等价槽位**的池子，`spi_slave_init()`
一次性全部用**合法 NODATA 帧头**预武装。主机取走一个，上层处理完就用
**同一个槽**填新应答再入队 —— 因为上层每轮必定回一帧，队列深度自然
维持在 3，空窗不再存在。

关键细节：备用槽的 `magic` **必须写对**。它代表"这轮从机没东西发"
（正常语义 `TUN_T_NODATA`），主机看到就跳过；若留全零，主机照样记
`bad_magic`，等于没修。

深度取舍：入队是 FIFO，应答排在已有槽位之后，要等 (SLV_DEPTH−1) 帧才上
总线。用 3 而不是 4，是为了把下行多出的延迟压在 ~5ms。每槽 4KB tx + 4KB rx。

配套改动：`spi_slave_wait_rx()` 增加 `slot_out` 参数；`spi_slave_arm_slot()`
新增；`spi_slave_next()` 变成空操作；`tunnel.c` 不再需要开头预武装。

### C. 🔴 新根因二：摄像头曝光滑块**根本无法工作**（平台限制，不是代码 bug）

### D. 🔴 根因三：三个脚本会"杀掉自己"（同一类 bug，踩了三次）

这是本轮最有价值的教训。BusyBox 的 `ps | grep X | awk '{print $1}' | kill -9`
是个**陷阱**：

| 脚本 | 自杀原因 |
|---|---|
| `S24spinet_wd` `stop_wd` | 模式 `[S]24spinet_wd` 会匹配到**管理员那条 ssh 命令**（`sh -c "...S24spinet_wd..."`），于是把自己的会话杀掉，表现为"SSH 跑一半卡死" |
| `S25mediamtx` `kill_mtx` | 模式 `[m]ediamtx` 会匹配到**脚本自身**（命令行 `/bin/sh /etc/init.d/S25mediamtx start`），于是脚本在 `setsid` 之前把自己 `kill -9`，表现为"开机后从不启动、日志文件压根不创建" |

`[x]` 这种写法**只能避开 `grep` 自己**，避不开其它命令行里含该串的进程。

**修复**：
- `S25mediamtx` 改用 `pidof mediamtx`（按**进程名**精确匹配）
- `S24spinet_wd` 的清扫排除 `sh -c`

另外 `S24spinet_wd` 还有一个独立问题：后台循环 `( ... ) &` **继承了 sshd
那一端的 stdout 管道**，导致 `ssh 板子 "/etc/init.d/S24spinet_wd restart"`
打印完输出后**一直不返回**直到超时。已改为 `</dev/null >> "$LOG" 2>&1 &`。
修复后同一条命令 **2.9 秒返回**。

### E. 🔴 根因四：udhcpc 守卫被刷机冲掉（老 bug 回归）

## 二十一、2026-10-05 第十五轮：**内核硬卡死** + 硬件看门狗

### A. 🔴🔴 事件：板子内核级硬卡死，只能物理断电

在最终验收压测跑到一半时，板子**彻底失联**：

```
WiFi 192.168.3.69:80/22   不通
有线 192.168.3.84:22      不通
USB 172.32.0.93:22        不通 (USB gadget 也没了)
```

而 **C5 还活着**（COM6 串口仍能打印 `wifi=UP rssi=-56`, `err=2`，堆 106KB）。
关键在于 C5 的计数器：

```
ip tx=3240 rx=6465 drop=271      ← 连续三次采样, 一个数都没变
sp tx=3240 rx=6465 drop=271      ← sp tx/rx 完全冻结
```

`sp tx` 是 C5 侧的 SPI 收发计数。**它不变 = 板子不再发起任何 SPI 传输。**
结合 eth0/USB 同时消失，判定是**内核级卡死**（panic 或驱动死锁），
而不是隧道问题、不是 C5 问题、不是网络问题。

等待 **3 分钟**没有任何自愈，最后只能请用户物理断电。

### B. 🔴 根因：这台板子的**硬件看门狗从来没开过**

排查发现：

```
/dev/watchdog*       : No such file or directory
/sys/class/watchdog/ : 空
/proc/device-tree/wdt*: 不存在
dmesg | grep watchdog: 无输出
```

而 SoC dtsi 里节点是有的，只是被禁用：

```dts
wdt: watchdog@ff5a0000 {
    compatible = "rockchip,rv1106-wdt", "snps,dw-wdt";
    status = "disabled";        // ← 这里
};
```

板级 dts **从来没有** `&wdt { status = "okay"; }`。

> 注意 `ps` 里那个 `31 root [watchdogd]` 是**内核线程**（方括号 = 内核线程，
> 是 softlockup/hardlockup 检测器），**不是**会喂狗的用户态守护进程。
> 很容易误以为"看门狗在跑"。实测板子上没有 `/sbin/watchdogd`，
> 只有 busybox 的 `/sbin/watchdog`。

### C. ⚠️ 为什么 userspace 看门狗救不了

这次的卡死是**调度器级别**的：所有进程都得不到调度。
任何"检测到没响应就重启"的 shell 脚本、Python 看门狗、systemd 式守护，
在这种状态下**都不会被执行**。

**只有硬件 WDT 有用**：它是一个独立的硬件计时器，用户态定期写
`/dev/watchdog` 喂它；一旦喂狗停止（因为系统根本不跑了），
硬件直接复位 SoC，不需要任何软件参与。

这正是需求里"长时间没有响应就重启"的**唯一正确实现方式**。

### D. ✅ 修复（本轮）

1. **设备树**：板级 dts 追加
   ```dts
   &wdt { status = "okay"; };
   ```
   内核侧 `CONFIG_DW_WATCHDOG=y` 在 `luckfox_rv1106_linux_defconfig`
   里本来就是默认值，所以只需要这一行。

2. **新增 `/etc/init.d/S21wdt`**：用 busybox `watchdog` 喂狗。
   - 超时 **30 秒**，喂狗间隔 **10 秒**
   - 为什么不用更短：单核 240MHz 同时跑视频+隧道+网页时偶有卡顿，
     超时太短会因为"某次繁忙"误复位，比不装还糟。而这个卡死是
     **彻底**的（不是慢），30 秒完全够。
   - 为什么不用更长：真死机后用户要等的时间 = 超时。
   - 用 **pidfile** 停进程，**不用** `ps | grep watchdog | kill` ——
     那个写法在本项目已经踩过三次坑（见二十节 D）。

3. **`tools/deploy/deploy-all.sh`** 加入 S21wdt。

### E. ⏳ 仍待解决：卡死的**根本原因**

硬件看门狗只是**兜底**（能自动恢复，但会中断图传和 SSH 几十秒），
根因还没完全定位。已掌握的线索：

| 线索 | 数据 |
|---|---|
| 卡死前的 load average | **11.55**（单核板子） |
| 大量 **D 状态**（不可中断睡眠）任务 | 有 |
| `[spitun]` 内核线程 wchan | **`spi_transfer_one_message`** |
| 卡死时 C5 侧 `sp tx/rx` | **完全冻结**（板子不再发起 SPI 传输） |

#### 🔴 已定位的一个真实驱动 bug：SPI 超时判断永不生效

读 `drivers/spi/spi-rockchip.c` 的 `rockchip_spi_pio_transfer()`：

```c
timeout = jiffies + msecs_to_jiffies(ms);
time = jiffies;                          // ← 循环外赋值一次
while (rs->tx_left || rs->rx_left) {
    ...
    cpu_relax();
    if (time_after(time, timeout)) {     // ← time 从不更新, 条件恒为假!
        ret = -EIO;
        goto out;
    }
}
```

**`time` 在循环里从不更新**，所以这个超时**永远不会触发** —— 只要
`tx_left`/`rx_left` 不清零，就是一个死循环。

而且前面还有：

```c
if (ms > UINT_MAX || ctlr->slave)
    ms = UINT_MAX;      // 从机模式 = 49.7 天
```

DMA 路径更彻底 —— 完全没有超时，`spi_sync` 最终走的是 SPI 核心里的
**无限 `wait_for_completion(&ctlr->xfer_completion)`**。只要 DMA 传输
永远不完成（比如 C5 忙于 WiFi 重连，没有把 4096 字节全部时钟出来），
调用线程就**永久阻塞在 D 状态**。这与观测到的
`wchan = spi_transfer_one_message` **完全吻合**。

**结论**：SPI 传输不完成时，内核没有任何兜底。这正是"硬卡死"的机制。

**下一步**（尚未做）：
1. 给 DMA 路径加超时（delayed work + `dmaengine_terminate_async` + 复位控制器）
2. 修上面的 `time` 不更新 bug（PIO 路径）
3. 或者评估强制 PIO（禁用 DMA）的 CPU 代价 —— 单核 240MHz 跑 4096B@20MHz
   需要 CPU 持续喂 FIFO，风险不小

> 在那之前，**硬件看门狗是唯一可靠的兜底**，它已经过实测验证（见下）。

### F. ✅✅ 硬件看门狗**已实测验证有效**

改完设备树、用 MTD 直写烧内核后，做了**决定性测试**：
打开 `/dev/watchdog` 但**从不写入**，模拟"喂狗进程得不到调度"的卡死状态。

结果：

| 观察项 | 测试前 | 测试后 |
|---|---|---|
| `uptime` | 293 秒 | **73 秒**（说明复位了） |
| `/tmp/wdt_test.log` | 存在 | **消失**（tmpfs 被复位清空） |

### G. 🎯 为什么用 MTD 直写烧内核（重要经验）

烧内核**不需要 maskrom、不需要拔电、不需要按 BOOT 键**：

```sh
# boot 分区是 mtd3 (4MB), 运行时没有被挂载
flash_erase /dev/mtd3 0 0
nandwrite -p /dev/mtd3 /tmp/boot_wdt.img
```

好处：
* **不打断使用** —— 不用物理接触板子
* **不会清掉 rootfs** —— `/etc/init.d` 里的脚本全都保住
  （整包刷 `update.img` 会全部冲掉，这是之前反复踩的坑）
* 只写 4MB，比整包快得多

本次实测：
```

源   md5 : 5327c96946f59bc57a1f9e9aea4372ad
读回 md5 : 5327c96946f59bc57a1f9e9aea4372ad   ✅ 完全一致
```

### H. ⚠️ 又一个"参数语义搞反"的坑（S21wdt 第一次启动失败）

busybox 的 `watchdog` 用法：

```
Usage: watchdog [-t N[ms]] [-T N[ms]] [-F] DEV
	-T N	Reboot after N seconds if not reset (default 60)   ← 硬件超时
	-t N	Reset every N seconds (default 30)                 ← 喂狗间隔
```

三个坑叠在一起：

1. **`-T` 是硬件超时、`-t` 是喂狗间隔** —— 和直觉相反。
2. **设备路径是位置参数**，漏了就只打印 usage 然后退出。
   第一次写的是 `-t 30 -T 10`（没给 DEV），开机必然失败，
   而 `/tmp/hw_wdt.log` 里只有一行 usage，看起来像语法错，
   实际是"少了一个参数"。
3. **`$!` 拿不到真正的 pid** —— `setsid watchdog ... &` 里的 `$!` 是
   **setsid 自己**的 pid，而 busybox `watchdog` 默认还会**再 fork 一次**
   变守护进程。实测进程明明在跑、`/dev/watchdog` 也确实被它打开，
   但 pidfile 记的是 setsid 的 pid，`kill -0` 立刻失败 →
   脚本误报"启动失败"。**必须用 `pidof watchdog` 取真实 pid。**

## 二十二、2026-10-05 第十六轮：🔴🔴 **失控** —— 完全没有失控保护

### A. 症状

用户报告"**控制失控**"。

### B. 🔴🔴 根因：网页只在**数值变化**时发指令，板子没有 deadman 保护

两处叠加，缺一不可：

**1) 网页端**（`index.html` 控制循环）：

```js
if(m !== lastMove){ pending = {path:'/api/move', ...}; lastMove = m; }
```

**只在数值变化时才发。** 所以按住摇杆不动时，**一条指令都不发**，
板子就一直保持最后那组向量。

**2) 板子端**（`web_server.py`）：

`STATE` 里有一个 `ts` 时间戳，每次指令都会更新，但
**整个文件里没有任何地方读它** —— 没有超时、没有 deadman、没有 failsafe。

于是只要出现下面任何一种情况，**车会带着最后的指令一直跑，松手也停不下来**：

| 触发场景 | 结果 |
|---|---|
| WiFi 抖动 / 隧道卡顿 | 车继续跑 |
| 浏览器标签页失焦、被系统冻结 | 车继续跑 |
| 页面崩溃 / 关掉 / 手机锁屏 | 车继续跑 |
| **板子内核卡死**（今天刚发生过一次） | 车继续跑 |
| **C5 重启**（刚刚也发生过） | 车继续跑 |

**这就是"控制失控"的机制。** 这是本轮最严重的问题 —— 前面所有工作都在
优化"通不通、快不快"，但**从来没做"断了怎么办"**。

### C. ✅ 修复：板子加 deadman + 网页加心跳（两边必须一起改）

**关键认识**：只改一边都是错的。

* **只改板子** → 用户按住摇杆不动时会被误判成失联，车**走走停停**。
* **只改网页** → 网页崩了 / 网断了就完全没人管，保护等于没有。

**板子端** `web_server.py`：
* 新增 `MOVETIMEOUT = 1.0` 与 `_failsafe_check()`
* `telemetry_loop` 的周期从 **1.0s 缩到 0.2s**，每轮调用保护检查
* 判据：只要 `vx/vy/w` 有一个非零、或 `dir` 不在 (`stop`,`brake`) 里，
  且**最近 1 秒内没有任何指令到达** → 立刻 `motor.stop()`
* 触发计数写进 `/api/status` 的 `failsafe` 和 `cmd_age`，便于量化观察
* 触发记录写 `/userdata/failsafe.log`

**网页端** `index.html`：
* 控制循环从 10Hz("变了才发") 改成 **5Hz 无条件发心跳**
* 仍然只保留最新一帧（`pending` + 在途标记），避免旧指令排队

### D. ⚠️ 为什么超时选 1.0 秒

* 网页心跳 200ms，1 秒 = **5 个周期**，能容忍单次丢包和隧道抖动
* 真失联时最多 1 秒就停 —— 对遥控车足够快
* 太短（比如 300ms）会在隧道抖动时频繁误停；太长（比如 3 秒）车已经跑出很远了

### E. ✅ 实测验证（板上跑的真实数据）

```
1) 发一次移动指令                  → dir=move  failsafe=0
2) 等 0.5s (窗口内)                → dir=move             ← 正确, 不误停
3) 等 2.0s (超时)                  → dir=stop  failsafe=1 ← 自动停车
4) 连续发 5 次心跳 (间隔 0.3s)      → dir=move             ← 正确, 不误停
5) 停心跳 1.5s                     → dir=stop  failsafe=2 ← 再次自动停车
6) 明确 stop                       → dir=stop
```

日志（`/userdata/failsafe.log`）：

```
2026-10-05 16:20:29 失联 1.15s -> 停车
2026-10-05 16:20:33 失联 1.31s -> 停车
```

**两种关键行为都验证过了**：失联 1 秒内自动停车；持续心跳时正常行驶不误停。

### F. ⚠️ 修复过程中自己踩的坑

日志一开始写不出来：写成了 `io.open(...)`，但 `web_server.py`
**没有 `import io`**（只 import 了 `json, os, sys, time, threading`）。
`NameError` 被 `_failsafe_check` 里那个"保护逻辑绝不能挂"的
`except Exception: pass` **静默吞掉**了 —— 保护功能是好的，但没日志。

改用内置 `open()` 后正常。

**教训**：为了健壮性而写的宽 `except` 会把真实 bug 藏起来。
那个 `except` 本身是对的（保护逻辑不该拖垮 telemetry），但**日志这种
不关键的操作，反而应该让错误可见**。以后这类"兜底 except"里至少要
`print` 一次。

## 二十三、2026-10-05 第十七轮：🎯 **控制延迟专项**（用户报"控制延迟高"）

### A. 先量化，不猜

写了三套测量工具，分别量三层，避免把"网络慢"和"前端慢"混为一谈：

| 工具 | 量什么 | 结果（修复前） |
|---|---|---|
| `_ctl_lat.ps1` | PC → 板子的 keep-alive `/api/move` 往返（真链路：PC→路由器→C5→SPI→板子）| 空载 **p50 23ms / max 45ms**（链路本身很快）|
| `ctl_browser_bench.js` | **真浏览器**（Edge headless + CDP）里"摇杆动作 → 请求发出"的时间 | 受固定 100ms 周期限制，最坏 ~100ms；抖动时整条链路被在途请求串行化 |
| `_hb_sim.ps1` + `_http_load.ps1` | 100ms 心跳在**批量负载**下的往返 | 负载加到 3.4 Mbps：**p50 95ms / p90 121ms / max 151ms，>100ms 占 40%** |

### B. 🔴 根因一：隧道每帧只装一个报文（排队延迟的根源）

`spitun.c` 的发送路径一次 `exchange`（固定 **3.1ms / 4096B 帧**）只塞**一个** ≤1350B 的报文
—— 帧里 2/3 是空的，包速率被钉死在 **≈333 pkt/s**，而 C5 侧 `tunnel.c` 早就实现了
"一帧多个报文"（按 `[2B len][packet]` 重复解析，注释里写着"highest single win available"）。
**板子这边没跟上**，于是：

* 批量流量（图传）把 64 深的 FIFO 灌满 → 控制指令/响应**排在大包后面**（队头阻塞）
* 实测：空载 23ms，加载 3.4 Mbps 后 **95ms** —— 3.4 Mbps 远低于隧道能搬的字节数，**瓶颈是排队不是带宽**

**修复**（`driver/spitun.c`，只改板子侧，**C5 固件不用改**）：

1. **每帧打包最多 3 个报文**（3×1352 = 4056 ≤ 4080，格式与 C5 解析端完全一致）
2. **小包优先队列**：载荷 ≤256B 的（`/api/move` 请求/响应、所有纯 ACK）走高优先级队列，
   大包（图传）走普通队列；组帧时先取高优先级队列，再补大包

### C. 🟡 根因二：前端把心跳卡在"上一条响应"上

上一版控制循环是 `setInterval(100)` + `sending` 在途标记：

* 人的操作最坏要等**一整个 100ms 周期**才被送出去（白送的延迟）
* `sending` 让**下一条指令必须等上一条响应回来** —— 隧道一抖（实测 RTT 能到 1s+），
  心跳就断，板子的 **1 秒失控保护被误判触发**，车一抖就停

**证据**：`/userdata/failsafe.log` 里 20 条记录，**全部集中在用户驾驶时段**
（18:20 / 18:21 / 18:28 / 18:29 四段 burst，每次"失联 1.0~1.4s -> 停车"）。

**修复**（`board/app/index.html`）：

* 25ms 巡检，**目标向量一变立刻发**（前导沿，最短间隔 60ms = 最坏 16Hz）
* 向量没变时按 100ms 发心跳（维持失控保护；停住只发一次 stop）
* 单次请求 **400ms 超时**（AbortController）→ 卡住的响应**再也不可能拖掉心跳链路**，
  超时后立刻补发最新一帧

### D. 🔴 根因三：C5 **欠压 brownout** 复位（约 2 秒全断）—— 硬件级

用 1Hz 采样 `c3_status` 抓到 `up_ms` **归零**（C5 重启），同期板子本地 `/api/move`
也从 16ms 变慢到 **215ms** —— 这是全链路 2 秒黑洞，正好落在"1 秒失控保护"的触发窗口里。
内存不是原因（`free` 恒在 112KB，远高于 30KB/12KB 两级保护线）。

**抓到 C5 串口日志（COM6 @115200，`tools/c3_serial_capture.ps1`），复位原因明确**：

```
E BOD: Brownout detector was triggered
rst:0x3 (RTC_SW_HPSYS),boot:0x18 (SPI_FAST_FLASH_BOOT)
```

**BOD = Brownout Detector = 欠压复位**，300 秒压测里 10 秒内连触发 2 次。

| 证据 | 说明 |
|---|---|
| **空载 200s 抓包：0 次复位**；图传+控制压测：几分钟内 5 次 | 只在 **WiFi 忙**时触发 → TX 突发电流尖峰拉垮 3V3 |
| `CONFIG_ESP_BROWNOUT_DET_LVL_SEL_7` | 阈值选了**最高档**（最敏感），轻微跌落就复位 |
| 固件里 `esp_wifi_set_ps(WIFI_PS_NONE)` | 关省电换低延迟 → 平均电流更高、峰值更猛 |
| 固件里**没有** `esp_wifi_set_max_tx_power()` | 一直按默认最大功率发射 |
| `rssi` −57 ~ −68 | 信号很好，功率有很大下调余量 |

**修复方向**（本轮未实施，需硬件或重编 C5 固件）：

* **硬件（推荐）**：C5 的 3V3 就近加 **220~470µF 电解 + 100nF 陶瓷**，缩短供电线、保证共地；
  若 C5 走 USB 供电，换短粗线/独立稳压 —— USB 线压降是这类尖峰复位的常见诱因
* **C5 固件**：`esp_wifi_set_max_tx_power(52)` = 13dBm（默认约 20dBm）；
  或把 brownout 阈值从 level 7 降到 4~5（治标，需配合硬件）
* 本机 WSL **没有 ESP-IDF 也没有 esptool**（C5 固件是在别处编的），所以这步要另行准备环境

**⚠️ 调试提醒**：**C5 的 USB 串口一被打开就会复位芯片**
（串口日志 `rst:0x15 (USB_UART_HPSYS)`——USB-Serial-JTAG 的 DTR/RTS 被主机拉动 = 请求复位）。
所以"开串口看日志"本身就会打断隧道，别把它当成故障；要抓**自发**复位就打开后一直别关。

## 二十四、2026-10-05 第十八轮：🔴 **"按了没反应"的真凶 —— 回程路由写死客户端 IP**

### A. 症状：板子侧一切正常，前端一切正常，就是没反应

用户："按了没反应，偶尔成功，有时候延迟执行。" 而现场三份数据都是好的：

| 观察点 | 结果 |
|---|---|
| PC → C3 ping | 正常（C3 在线） |
| 隧道 / 模块 / web 服务 | 正常（`spitun` 已加载、:80 在监听） |
| 板子本地 `/api/move` | **12ms**，CPU 66~72% 空闲 |
| 前端发的指令 | trace 里**看得到**（`/api/move {"vy":1,...}` 确实到了板子） |

### B. 根因：回程路由写死了 `192.168.3.64`

`S22spinet` 里 `CLIENTS="192.168.3.64"` + `ip route replace $c/32 dev spitun0`。
**用户 PC 的 DHCP 地址变成了 192.168.3.65**（重启/租约到期）→ 板子的回包
查不到 .65 的路由 → 从默认路由（usb0/169.254）发出去 → C5 的 NAPT 不认 → 丢包。

**最狠的一点**：回包发不回去，**TCP 三次握手都完不成** —— SYN-ACK 是内核发的，
根本轮不到 HTTP 处理器。所以浏览器只看到"超时/没反应"，板子上没有任何错误。

实测：手工补 `ip route replace 192.168.3.65/32 dev spitun0` → **HTTP 立刻恢复**。

> 这也是为什么之前所有"控制延迟"的测量都是好的：链路没问题，
> 是**回包路径**在客户端换 IP 后整体失效。

### C. 修复：源地址策略路由

```sh
ip rule add from 10.77.0.2 lookup 100 pref 100
ip route replace 192.168.3.0/24 dev spitun0 src 10.77.0.2 table 100
```

* 隧道侧发出的包源地址恒为 **10.77.0.2** → 查表 100 → 回隧道
* 网线侧发出的包源地址是 eth0 的 → 走主表，**完全不受影响**
* **不需要知道客户端是谁**，DHCP 怎么变都不会失联

写进 `board/init.d/S22spi-tunnel`（开机装）与 `board/init.d/S24tunnel-watchdog`（故障撤掉、恢复补回）。

### D. ❌ 走过的弯路（重要）

先在 `web_server.py` 里做"每请求自愈"（检查 client_ip 缺路由就补）—— **实测无效**：
删掉路由后 HTTP 直接超时，自愈日志**一行都没有**。原因就是上面那条：
握手完不成，处理器不会被调用。**这一层修不了，必须在路由层修。**

### E. ✅ 验证

* 删掉 .65 的 /32 后只靠策略路由：PC HTTP 正常、控制往返 **p50 27ms**
* **重启验证**：`ip rule` / 表 100 开机自动生效；PC（.65，无静态路由）HTTP 正常
* 真浏览器：动作→请求 **p50 14ms**、心跳 124ms、JS 异常 0

## 二十五、2026-10-05 第十九轮：🎯 **控制不丢包 + 低延迟（用户要求"彻底解决"）**

### A. 丢包到底丢在哪 —— 先量清楚

| 层 | 观测手段 | 结果 |
|---|---|---|
| SPI 帧 | `bad_magic` / `fail` 计数 | **稳态 ~0.6~4%，但突发到 30%**（板子/C5 刚上电那 30 秒：12316 帧里 3715 帧失败）|
| 隧道发送队列 | `ip_drop` | 一次满载测试 **593 个包被丢**（队列 64 深被打满）——全是 TCP 段 |
| 端到端控制 | 300 条 keep-alive 指令 | 丢包很少，但**长尾很重**（TCP 丢一段就要等 RTO ≥200ms）|

**关键认识：隧道层没有重传，丢一帧 = 那一帧里的 IP 报文永久消失**，
只能靠 TCP 自己重传，而 Linux 的 RTO 起步就是 **200ms**、指数退避到几秒。
所以"偶尔丢一帧"在用户侧就是"控制一顿一顿、延迟忽高忽低"。

### B. 三个改动（都在板子这一侧，**不用改 C5 固件**）

| # | 改动 | 为什么 |
|---|---|---|
| 1 | **帧级重传** `EXCH_RETRY=3`：exchange 失败（bad_magic）就在最底层**立刻重发同一帧**，退避 0.2~0.4ms | 丢一帧在这里只要 **~3ms** 就能补回来，而让 TCP 兜要 **200ms+** |
| 2 | **发送队列 64 → 256** | 突发（关键帧/HTTP 洪峰）不再打满队列丢包：`ip_drop` 593 → **0** |
| 3 | **sysfs 计数器** `/sys/class/net/spitun0/tun_stats` | 随时能读丢包/重传/队列数据（dmesg 那条 16 参数的长行在这块板子上**根本没打出来**，别再依赖它）|

（第 23 轮已有的"小包优先队列 + 每帧打包 3 个报文"继续生效。）

### C. ✅ 验证：boot 阶段与满载阶段

**① 复位 C5 强制造故障**（从机消失 2 秒）：

```
bad_magic=611 → retry=611 → fail=203
```
—— 重传机制确实在按帧工作；C5 整机消失 2 秒这种是**补不回来**的（预期之内），
但**孤立单帧失败**（稳态的全部情况）能被补掉。

**② 重启后开机阶段（历史上丢包最凶的窗口）**：

```
frames=23352 ok=23352 fail=0 bad_magic=5 bad_csum=0
retry=5 retry_ok=5          ← 5 次失败, 5 次全部重传成功
ip_drop=0
```

**`fail=0` —— 开机阶段一帧都没丢给上层。**

**③ 满载（720p 图传 + 9.2 Mbps 批量 + 控制同时跑）**：

| 指标 | 本轮开始（修复前） | **现在** |
|---|---|---|
| 控制丢包 | 有长尾，>100ms 占 40% | **200/200 全到，0 丢包** |
| 控制 RTT | p50 95 / max 151ms | **p50 36 / p90 61 / p99 77 / max 78ms** |
| >200ms 次数（TCP 重传） | 常见 | **0** |
| 隧道帧失败 | 累积上万，突发 30% | **0**（该窗口内）|
| 隧道队列丢包 `ip_drop` | 593 | **0** |
| 批量吞吐 | 3.42 Mbps | **9.21 Mbps** |
| 图传 | 卡顿 | 130 秒里播了 128.35 秒 |
