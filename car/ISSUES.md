- C3 的 `REV_PORTS = {80, 22, 8889, 8189, 8888}` —— 每个端口一个反向代理

## 可疑点（未验证，按可能性排序）

### 🔴 1. `web_server.py` 是否在重启？
- **线索**：曾观察到 `"uptime": 3`（进程只跑了 3 秒）
- **但**：用户手动重启过，所以那次数值正常
- **待验证**：连续采样 `uptime`，看是否单调递增；若反复归零 = 崩溃循环
- **影响**：进程重启 → 页面无响应 = "板子离线"

### 🔴 2. SPI 隧道在高负载下丢帧
- **线索**：`fails` 计数曾暴涨到 37291 / 126734
- **机制**：隧道**无重传**，丢帧 = 数据永久丢失
- **关键**：图传和控制共用隧道，隧道抖动会同时影响两者
- **待验证**：跑压力测试，观察 `fails` 增长速度

### 🟡 3. C3 仅 8 个反向代理槽位
- **线索**：`MAX_REV = 8`，每槽位占 `REV_RXBUF(2048) + REV_TXBUF(4096)`
- **影响**：浏览器/播放器连接不及时释放 → 槽位占满 → 新连接被拒
- **待验证**：观察 `rev 槽位 N/8 占用` 是否经常接近 8

### 🟡 4. 单核 CPU 争抢
- **线索**：板子只有 1 个 A7 核
- **影响**：`spinet` 忙轮询 SPI + `rkipc` 编码 + `mediamtx` + `web_server` 互相抢 CPU
- **已优化**：`sys.setswitchinterval(0.0005)` 让出 GIL
- **待验证**：`top` 看 CPU 占用，看 `idle` 是否常为 0

### 🟡 5. WebRTC 抖动缓冲
- **线索**：延迟约 129ms ≈ 3 帧 @25fps
- **影响**：隧道抖动 → 抖动缓冲膨胀 → 感知为"卡顿/断线"
- **注意**：这是**延迟**问题，不一定导致**断线**

### 🟢 6. WiFi 兼容模式双 BSSID
- **线索**：路由器曾同时广播 `ABC` 和 `ABC_Wi-Fi5`（同 ch6）
- **影响**：同信道双 BSSID 可能互相干扰
- **待验证**：关掉"WiFi5 兼容模式"看是否改善

# ✅ 已修复：SPI 忙轮询独占单核 CPU

**修复日期**：2026-09-23
**状态**：已部署并验证

## 确定性证据（修复前）

| 指标 | 实测 | 正常 | 结论 |
|---|---|---|---|
| `spinet.py` 累计 CPU | **29383 jiffies** | — | 是 rkipc(4715) 的 **6.2 倍** |
| `pump` 帧率 | 143→205→228 | 350-400 | 掉 **60%** |
| `fails` | 15→84 持续增长 | 基本不涨 | **持续丢帧（无重传，永久丢失）** |
| CPU `idle` | 0-30%（出现过 0%） | 充裕 | **CPU 满负荷** |
| rssi | **-52~-59（优）** | — | ❌ 与信号无关 |
| `spinet_pid`/`web_pid` | 全程不变 | — | ❌ 非重启/非崩溃循环 |

## 根因

板子只有 **1 个 A7 核**。`pump()` 是**无 yield 的忙轮询**：

```python
while self.running:
    r = self.spi.exchange(T_APP, payload)   # 没有任何让出 CPU 的点
```

它把 CPU 吃满 → `rkipc`（视频编码）/ `mediamtx` / `web_server` 抢不到 CPU →
- 图传数据来不及处理 → **断线**
- 控制指令排队 → **失效**
- SPI 帧处理不及时 → **丢帧**

**这解释了"有时好有时坏"**：CPU 一紧张就崩，一缓过来就恢复。

## 修复

在 `pump()` 加入**有界自适应退让**，只在**双向都空闲**时才 `sleep(1ms)`：

```python
idle_streak = 0
...
if not payload:
    idle_streak += 1
    if idle_streak >= 2:
        time.sleep(0.001)   # 最坏只多 1 帧延迟
else:
    idle_streak = 0
```

**1ms 的取舍**：从机是 store-and-forward，主机必须持续发帧才能取回 C3 数据。
1ms 既让出 CPU，又不会让从机饿死。

## 修复后实测（决定性改善）

| 指标 | 前 | **后** | 改善 |
|---|---|---|---|
| **pump 帧率** | 143-228 | **354-382** | **+67%** |
| **`fails` 增速** | 每 20s +13~20 | **每 20s +1** | **↓95%** |
| **spinet CPU** | 29383 jiffies | **38%** | ↓40% |
| **CPU idle** | 0-30% | **38%** | 稳定 |
| CPU 分布 | spinet 独占 | 38% / 9% / 3% / 3% | 均衡 |

**端到端验证**：
- 控制指令 **8/8 成功，0 失败**（222~516ms）
- 图传端口 :8888/:8889/:8189 全部 OK（70~117ms）
- C3 内存健康：`free=131560`, `minfree=91724`

| ping | 0% 丢包，5–18ms |

## 修复的三个真实 bug（都有实测证据）

### 1. 视频分片尾部被丢弃（图传不能看的直接原因）

**症状**：控制正常，图传失败。C3 日志 `rx=0 tx=0`。

**根因**：板子读完本地响应后发 `APP_CLOSE`，但此时大响应（视频分片 40KB+）
还有大量帧在途；C3 收到 CLOSE 立刻释放槽位，尾部帧到达时无处可去：

```
W revproxy: feed miss id=... len=642 (slot gone)
```

**为什么控制不受影响**：控制响应约 187 字节 = 1 帧，不触发。
**为什么图传必挂**：分片 40KB = 10+ 帧，尾部必丢 → 播放器判定分片损坏。

**修复**：
- C3 `rev_worker` 退出前**先排空 TX 缓冲**（最多 300ms）再释放槽位
- 板子 `self_drain` 返回值检查，drain 超时才放弃，超时从 2s 提到 10s

**验证**：`feed miss` 计数归零；relay 日志 `读 46831, 推 46831`（读=推，零丢失）。

### 2. 每次新建连接固定多 300ms 延迟

**症状**：控制延迟 492ms，且异常稳定（484–510ms）—— 固定延迟说明有写死的 sleep。

**根因**：`_accept_reverse` 里有个 `time.sleep(0.3)`，是我早先为规避"陈旧 CLOSE"
加的权宜之计，给**每次新连接**硬加 300ms。

**修复**：删掉 sleep，改用 `relay_socket` 里正确的 `armed` 守卫 ——
只有**真正发生过数据交换**之后才理会 CLOSE（此前版本把 `armed` 写成
"state 不是 closed"就置位，而 state 在启动前已被清空，守卫形同虚设）。

**验证**：控制 p50 **492ms → 196ms**（降低 60%）。

### 3. 槽位复用时的 4KB 缓冲泄漏

**症状**：`largest free block` 在一次运行中掉了**正好 4096 字节**（= REV_TXBUF）。

**根因**：`rev_accept_task` 里 `memset(r, 0, sizeof(*r))` **无条件清零槽位**，
若该槽位的 `tx` 尚未释放，指针永久丢失 → 4096 字节再也找不回来。

**修复**：memset **之前**先 `free(r->tx)`。

## 新增：分级内存保护（自恢复）

实测每连接消耗约 213 字节（lwIP 协议栈对象，负载降低会部分回收，
在 ~111KB 处收敛）。为防止将来内存紧张时**楔死**（需要人工复位），加了分级保护：

| 剩余堆 | 动作 |
|---|---|
| < 30KB | `revproxy_drop_all()` —— 丢弃所有反向代理槽位，回收缓冲 |
| < 12KB | `esp_restart()` —— 重启（板子自动重新握手，已验证）|

**重启是安全的**：板子 `spinet.py` 能检测到 C3 重启并重新握手。

## 新增：无线诊断字段

`192.168.3.69:10000` 发 `stat` 返回 JSON，含泄漏定位所需字段：

```json
{"ip":"192.168.3.69","rssi":-75,"free":111080,"minfree":71636,
 "largest":110592,"tasks":16,"slots":0,"workers":0,"up_ms":528000}
```

- `largest` 与 `free` 对比 → 区分**真泄漏**和**碎片化**
- `tasks` / `workers` → 判断 worker 任务是否被回收
- `slots` → 槽位记账是否泄漏

# 🔴 2026-10-05 19:2x：**"按了没反应 / 偶尔才动"** —— 现场判定（软件 vs 电压）

用户报"按了没反应，偶尔成功，有时候延迟执行"。用板子侧指令追踪
（`/userdata/cmd_trace.log`，`do_POST` 里按需记录）+ C5 串口 + 单进程观测器
`fs_watch.py` 三方对齐后，结论如下。

## 1. ✅ 指令链路是通的（不是网络/前端不通）

按下的瞬间板子确实收到了指令，且**发一条就立刻被 stop 跟上**：

```
19:24:30 :56314 /api/move {"vx":0,"vy":-1,"w":0,"s":30}   x3
19:24:30 :56314 /api/cmd  {"c":"stop"}
19:24:30 :56314 /api/move {"vx":0,"vy":+1,"w":0,"s":30}   x3
19:24:30 :56314 /api/cmd  {"c":"stop"}
```

- 3 条相同 move = **前导沿 + 100ms 心跳**（第 23 轮的新前端逻辑），说明前端在按预期工作
- 每条 move 后面紧跟 stop = 用户是**短按**（约 300ms）；电机只拿到 ~300ms 的驱动
- 板子本地 `/api/move` 往返 **12~17ms**，CPU **66~72% idle**，隧道 `bad_magic/fail = 0`

## 2. 🔴 真正的直接原因：**整车在靠 USB/调试线供电，电池没接或没开**

用户确认："主要靠 USB/调试线供电，电池没接或没开"。

`car/WIRING.md` 里**早就记过同一个坑**：

> ⚠️ 供电（必须电池，不能用板子USB）
> 电机走板子 USB 供电 → 电机启动拉垮供电 → **板子欠压掉线**；
> 改电池供电后板卡→云丢包从 **20~23% 降到 0%**

机制（与实测证据一一对应）：

| 现象 | 机制 |
|---|---|
| 按下后偶尔才动 / 延迟执行 | 电机启动瞬时电流把 USB 5V 轨拉垮 → 板子/C5 掉压 → 那几帧指令丢了或迟到 |
| C5 串口 `E BOD: Brownout detector was triggered` / `rst:0x3` | 同一根 5V 轨欠压，WiFi 发射 + 电机电流叠加时触发 |
| 隧道整段黑 2 秒、失控保护误停 | C5 复位 → 隧道要重新握手 |
| 电池页显示 9.35V | **电池没接时 ADC 读的是悬空值，这个数字没有意义**，不能当电量看 |

## 3. 🟡 次要原因：旧页面（已修）

用户浏览器里那个页面是**上午 10:43 打开的**，而前端控制循环傍晚才改。
旧 JS "只在数值变化时才发" → 按住不动时板子 1 秒收不到指令 → 失控保护停车 →
"走走停停 / 延迟执行"。已在 `index.html` 修好，并新增**陈旧页面自检**：
`/api/status` 带回 `ver`（index.html 的 mtime），页面发现文件变了会自动 reload。

## 4. ⚠️ 我自己踩的坑：诊断脚本把单核板子打满

`_fs_watch.sh` 原来是 `sh` 循环里每 0.5s 起一个 `python3 -` ——
**Python 启动在单核 A7 上要几百毫秒**，于是"观测器"自己把 CPU 打到
**0% idle**，web 线程和 250Hz 软件 PWM 线程一起被饿死。
恰好覆盖用户按键盘的那段时间，直接造成了一轮"按了没反应"。

已改成单进程常驻 `fs_watch.py`（开销 <1%）。
**教训**：在这块板子上，任何"循环里起 python 进程"的脚本都是故障源。

# 🔴🔴 2026-10-05 21:xx：**"按了没反应"的真凶 —— 回程路由写死了客户端 IP**

## 症状（极具误导性）

网页和控制**完全没反应**；但从板子侧看**一切正常**：
C5 在线（能 ping 通 192.168.3.69）、隧道正常、模块已加载、web 服务在监听、
CPU 空闲、板子本地 `/api/move` 只要 12ms。前端也在正常发指令（trace 里能看到）。

## 根因

`/etc/init.d/S22spinet` 里回程路由**写死了一个客户端 IP**：

```sh
CLIENTS="192.168.3.64"
ip route replace "$c/32" dev spitun0
```

**用户 PC 的 DHCP 地址从 192.168.3.64 变成了 192.168.3.65**（重启路由器/租约到期）。
于是板子的回包查不到 192.168.3.65 的路由 → 落到默认路由（usb0/169.254）发出去
→ C5 的 NAPT 不认这个包 → **包直接消失**。

关键点：**回包发不回去，连 TCP 三次握手都完不成**（SYN-ACK 是内核发的，
轮不到 HTTP 处理器）。所以浏览器那边表现为"连接超时/没反应"，
而板子侧完全没有错误可看。

实测：补一条 `ip route replace 192.168.3.65/32 dev spitun0` → **HTTP 立刻恢复**。

## 修复：源地址策略路由（不再需要知道客户端是谁）

```sh
ip rule add from 10.77.0.2 lookup 100 pref 100
ip route replace 192.168.3.0/24 dev spitun0 src 10.77.0.2 table 100
```

* 板子经隧道发出的包，**源地址恒为 10.77.0.2** → 查表 100 → 回隧道
* 网线侧发出的包，源地址是 eth0 的地址 → 走主表，**完全不受影响**
* 客户端是 .64 / .65 / 手机，或者以后再变，**都不用改配置**

已写进 `S22spinet`（开机自动装）和 `S24spinet_wd`（故障时撤掉、恢复时补回）。

## ❌ 走过的弯路（记录下来，别再试）

一开始想在 `web_server.py` 里"每个请求自愈"：检查 client_ip，缺路由就补一条。
**实测无效**：删掉路由后 HTTP 直接超时，自愈代码**一行日志都没有** ——
因为 SYN-ACK 是内核发的，握手都完不成，HTTP 处理器根本不会被调用。
**这一层修不了，只能修路由层。**

## ✅ 验证

* 删除 .65 的 /32 路由后，只靠策略路由，PC 的 HTTP 与控制**全部正常**（p50 27ms）
* **重启验证**：`ip rule` / 表 100 开机自动生效，PC（.65，无静态路由）HTTP 正常
* 真浏览器实测：动作→请求 p50 **14ms**，心跳 124ms 稳定，JS 异常 0

# 🔴🔴 2026-10-05：C5 偶发重启 = **欠压 brownout**（控制卡顿的硬件级根因）



## 症状

驾驶时控制"一抖一停"：板子 1 秒收不到指令 → 失控保护停车 → 2 秒后恢复。
`/userdata/failsafe.log` 里 9 分钟内触发 **20 次**，全部集中在驾驶时段。

## 定位过程（可复现）

1. 1Hz 采样 `/sys/class/net/spitun0/c3_status` → 抓到 `up_ms` **归零**（C5 重启），
   同期板子本地 `/api/move` 也从 16ms 变慢到 **215ms**
2. 内存不是原因：`free` 恒在 **112KB**（远高于 30KB/12KB 两级保护线）
3. **抓到 C5 串口日志（COM6 @115200）**，复位原因明确：

```
E BOD: Brownout detector was triggered
rst:0x3 (RTC_SW_HPSYS),boot:0x18 (SPI_FAST_FLASH_BOOT)
```

**"BOD" = Brownout Detector = 欠压复位。** 10 秒内连触发 2 次。

## 为什么是欠压

| 证据 | 说明 |
|---|---|
| 只在 **WiFi 忙**时触发（跑图传 + 控制压测时 300s 内 2 次）| WiFi TX 突发电流尖峰把 3V3 拉垮 |
| ESP-IDF 配置：`CONFIG_ESP_BROWNOUT_DET_LVL_SEL_7` | 阈值选的是**最高档**（最敏感），轻微跌落就复位 |
| `esp_wifi_set_ps(WIFI_PS_NONE)` | 关省电（为了低延迟）→ 平均电流更高，峰值更猛 |
| 固件里**没有** `esp_wifi_set_max_tx_power()` | 一直按默认最大功率发射 |
| `rssi` −58 ~ −68 | 信号很好，**功率有很大下调余量** |

## 修复方向

**A. 硬件（最彻底，推荐）**
- C5 的 3V3 就近加 **220~470µF 电解 + 100nF 陶瓷**，缩短供电线，
  保证 GND 回流通畅 —— 专门吸收 WiFi TX 的 µs 级电流尖峰
- 若 C5 由 USB 供电，换短粗线/独立 5V→3V3；USB 线压降 + 限流是常见诱因

**B. C5 固件（需 ESP-IDF 重编 + 串口烧写）**
- `esp_wifi_set_max_tx_power(52)`（13dBm，默认约 20dBm）→ 峰值电流显著下降，
  信号 −60 完全够用
- 或把 brownout 阈值从 level 7 降到 4~5（`CONFIG_ESP_BROWNOUT_DET_LVL_SEL_x`），
  容忍瞬态跌落（治标，但要配合 A 才安全）

## ⚠️ 调试提醒（踩过的坑）

**C5 的 USB 串口一被打开就会复位芯片**（串口日志 `rst:0x15 (USB_UART_HPSYS)`）：
USB-Serial-JTAG 的 DTR/RTS 被主机拉动 = 请求复位。
所以"开串口看日志"本身就会打断隧道，别把它当成故障。
要抓**自发**复位就打开后一直别关（`c3_serial_capture.ps1` 就是这么做的）。

- 控制延迟：**p50 约 200ms**（曾 492ms）
- 视频分片：46–72KB 每个，全部完整
- C3 掉线：**0 次**
- ping：0% 丢包，5–18ms

## 内存结论：不是泄漏，会完全回收

曾观察到活动时 C3 堆持续下降（约 213 字节/连接），一度以为泄漏。
但长时间观察后**堆回到满值 142996**：

```
活动时: 106424
空闲后: 142996   ← 完全恢复
```

说明那是 lwIP 协议栈内存池在负载下扩张、空闲时归还，**不是真泄漏**。
（这也解释了为什么两次测试之间 free 会回升。）

仍保留分级保护作为兜底（30KB 回收槽位 / 12KB 重启）。

## 看门狗升级：从"查进程"到"查数据面"

**原来的缺口**：旧看门狗只检查 spinet **进程是否存活**。但 C3 复位后，
板子的 SPI 主机还握着旧事务流水，两边失配 —— **进程活着但数据完全不通**。
这个状态以前必须人工重启 spinet，而隧道本身就是远程通道，所以等于失联。

**现在**：C3 每秒推一帧状态，spinet 写入 `/tmp/c3_state.json`。
看门狗检查该文件年龄，**超过 45 秒没更新就重启隧道**。

```
spinet-wd running (pid 3753), state age 0s
log: "tunnel down -> restarting"      ← 已实际生效
```

**实测有效**：本轮安装后日志显示它已自动重启过一次隧道。

## 现在的行为

| 故障 | 自动恢复 |
|---|---|
| spinet 进程死亡 | 看门狗 20s 内重启 |
| 隧道假死（数据不通） | 看门狗 45s 内重启 |
